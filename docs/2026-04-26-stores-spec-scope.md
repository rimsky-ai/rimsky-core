# Stores Redesign — Spec Scope Working Document

## Status

- 2026-04-26 brainstorm working document. Drives the conversion of `docs/2026-04-26-stores-redesign.md` into a formal spec.
- §19 of the discussion doc is authoritative wherever it differs from the in-line text in §§4–15.
- Spec destination: `docs/specs/2026-04-27-stores-redesign-v2-design.md`.
- Multi-tenant store provisioning is out of scope; lives in `docs/2026-04-26-control-layer.md`.

## Five-item forward-looking sweep — locked

| # | Item | Disposition | Principle / note |
|---|---|---|---|
| 1 | §14.8 #4 — operator deployment recipes (mTLS / per-tenant bridge / encrypted-credential pass-through) | Drop | Auth-blind doc pass (I7) covers `operator-guide.md` without a recipe catalog. Per-tenant bridge is a multi-tenant concern; multi-tenant is out (Item 5). |
| 2 | §19.6 step 6 — reference encrypt-before-pass helper library | Drop | Rimsky is not in the encryption helper library business. Future encryption support, if any, is baked-in protocol-level (way down the road) or nothing. Store authors bring their own crypto. Offering a Go helper implies offering one per language; offering none is the consistent stance. |
| 3 | §17 #2 — bridge framework / Go SDK | Drop | Rimsky specs the protocol; implementers handle SDKs / frameworks / helpers. Same principle as Item 2. Rimsky users are coding-agent-fluent; library hand-holding is not earned. |
| 4 | §17 #5 — bridge-vs-scheduler enforcement of read leases | Drop, revised | Already settled by blessed invariant 9 (lock state lives only in postgres). Scheduler is sole lock authority. §9 strategy 2 (reader-lease serialization in the store service) is **forbidden**, not optional — it moves lock state into the store service and violates invariant 9. Same anti-pattern §4.2 already flags. Spec restates this principle in `store-author-guide.md`. |
| 5 | §15 — multi-tenant stores | Drop entirely | Control-layer concern; runtime sees stores uniformly. No `SupportsProvisioning` capability flag, no admin verbs, no `rimsky_substores` table in this spec. See `docs/2026-04-26-control-layer.md` §1. |

**Carried principles that affect the rest of the table:**

- "Not in helper library business" → drops F8 (`payload_encryption` informational field) since its only purpose was to signal helper-library variant.
- "Strategy 2 forbidden" narrows the §9 design space for `staged_async` to strategy 1 (snapshot delegation) or strategy 3 (native MVCC pass-through) only — relevant if/when we settle async-read in v1 (M1).

| **C. Claim / lock model** | | | | |
| C1 | Two primitives, distinct vocabulary (revised 2026-04-27) | **Claim** — substrate-bound; has `(store_name, region_data, intent)` where intent ∈ {`r`, `rw`}. **Named lock** — not substrate-bound; has `(lock_name, limit)`. Both materialise as rows in `rimsky_lock_holders`; both halt nodes when held. They are different primitives with different shapes, identities, coexistence rules, and lifecycle verbs. The spec uses these two distinct nouns; "claim" never refers to a non-substrate-bound thing, "named lock" never refers to a substrate-bound thing. | §19 settled, conversation 2026-04-27 | Yes |
| C1.1 | Why one shared table | Both kinds answer the same operational question — "given existing holders, can this new acquirer proceed?" — and share the surrounding machinery: atomic acquisition transaction, heartbeat refresh, orphan reap, claimant-guarded release, cross-cutting observability. Two tables would duplicate every row of that machinery. The cost — one CHECK constraint enforcing exactly-one-of-(`lock_name`)-or-(`store_name`+`region_data`) — is paid once. | conversation 2026-04-27 | Yes |
| C2 | Named-lock coexistence rule (purely numeric) | One rule: `count(existing holders for this lock_name) < limit → acquire OK`. No read/write distinction. No async/sync axis. Every named-lock holder is interchangeable. Mutex (limit=1) and counting (limit=N) are the same primitive with different limit values. | §5.2 + conversation 2026-04-27 | Yes |
| C3 | Claim coexistence — two binary axes (revised 2026-04-27) | A claim's effective mode is derived from two binary axes: **sync vs. async** (per-store, from `write_semantics` — `direct` and `staged_blocking` are sync; `staged_async` is async) and **r vs. w** (per-claim, from intent). Four combinations: `sync-r`, `sync-w`, `async-r`, `async-w`. Mode is **not stored** on the lock-holder row — it's computed at conflict-check time from `(intent, store.write_semantics)`. | §5.2 + conversation 2026-04-27 | Yes |
| C3.1 | Coexistence matrix (4×4 collapsed to two diagonal blocks) | Two claims on overlapping regions on the same store. **Sync block** (`direct` / `staged_blocking`): r×r ✅, r×w ❌, w×w ❌. **Async block** (`staged_async`): r×r ✅, r×w ✅, w×w ❌. Cross-quadrant cells (sync × async) don't arise — two claims on the same store share its `write_semantics`. The w×w ❌ in both blocks is the structural single-writer-per-region rule (C4), folded in. | conversation 2026-04-27 | Yes |
| C3.2 | Why both axes are needed | Read/write alone is insufficient (r×rw blocks under sync but coexists under async). Sync/async alone is insufficient (under sync, r×r coexists but rw×rw doesn't; under async, w×w blocks). The 4-way subdivision is the minimum to express the rule set without ambiguity. | conversation 2026-04-27 | Yes |
| C4 | Single-writer-per-region | Structural invariant: at most one `rw` claim on overlapping regions at any time, regardless of mode. Folds into the w×w ❌ cell in both coexistence blocks; not a separate mechanism. Enforced by the dispatch claim machinery as part of the conflict predicate. | §19 settled | Yes |
| C5 | Substrate-side fences brief | Brief, applied at commit (staging + atomic swap). Run-spanning substrate locks are an anti-pattern (§C5 in store-author guidance — restate alongside invariant-9). | §4.2 | Yes |
| C6 | Substrate commit failures | Surface as `Commit` errors; route through existing `retry / give_up / invalidate` vocabulary. No new error class. | §4.3 | Yes |
