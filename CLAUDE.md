# CLAUDE.md

Rimsky is a project-agnostic reactive node-graph orchestration platform. This file is a pointer index — per rimsky's own "After Code Changes" rule, keep CLAUDE.md lean and only update it when something a future session would otherwise trip over has changed.

## Where to look first

**Architecture, concepts, decisions** — `.ok-planner/design/concepts.md` is the TOC; per-noun definitions and boundaries live under `.ok-planner/design/concepts/<slug>.md`, and the choices and user promises behind them live beside it under `decisions/` and `stories/`. The design corpus is the durable design surface, updated alongside code by sprint execution (corpus deltas applied verbatim from `/plan-sprint` sprints), and is the authoritative source for ownership and for the choices the project has made. Start with `concepts/module-layout.md` for the four-module / four-layer split: the repo root holds four idiomatic top-level code directories — `cmd/` (binaries), `lib/` (shippable library code), `test/` (out-of-tree tests + their machinery), `tools/` (dev tooling). Library packages live under `lib/` (`lib/protocols`, `lib/foundation`, `lib/services`, plus the root-module `lib/graph` → `lib/runtime` → `lib/control` layer ordering); `lib/services` holds the bundled consumption-side services (claim_producers, sensors, subscribers, executors) shipped as images — its shipped packages depend only on `lib/protocols`, with isolation from core internals enforced by lint (the module's manifest also requires the root module and `lib/foundation`, but only for its own out-of-tree test tree, which never ships); test scaffolding lives under `test/support/`.

**Enforced import boundaries** — `.golangci.yml` `depguard` block (`pgx-isolation`, `foundation-internal-isolation`, `protocols-purity`, `foundation-purity`, `graph-purity`, `runtime-purity`, `consumption-side-isolation`). If lint and prose disagree, lint wins. `go.work` ties the four Go modules together (root, `lib/foundation`, `lib/protocols`, `lib/services`).

**Load-bearing safety properties** — recorded in the decisions and stories under `.ok-planner/design/` and proven by tests: the scenario tests under `test/scenarios/` and the ordinary suites. A concept defines a noun and states no safety property. There is no in-code or in-prose tag form and no numbered catalog; the decision or story is the record, the test is the proof.

**Concept-to-code links** — `grep -rn '@concept:' .` in source.

**Open / unresolved design questions** — `.ok-planner/issues/` (one markdown file per question, ruling-ready via `/verify-issues`; promoted or retired via `/plan-sprint`). The former `design/tensions/` directory is migrated: live tensions became issue rows, the files are archived under `.ok-planner/history/tensions/`.

**Build commands** — `Makefile`. Standard targets: `make build-all`, `make test-all`, `make lint`, `make tidy`, `make proto-gen`. `make build-all` / `test-all` / `lint` now also cover the `lib/services` module. `make service-images` builds the bundled-service images (one per claim_producer / sensor / subscriber / executor under `lib/services/`). Scenario and storage tests under `test/scenarios/...` and `lib/foundation/persistence/...` use testcontainers-go and require a working Docker socket.

**Public docs** — not part of this repo. This tree carries no docs sources, no docs-lint tooling, and no docs gate.

**Image builds** — Dockerfiles live in `dockerfiles/` (core) and co-located with each service under `lib/services/`. `make core-images` builds the four distributed core images: `rimsky` (all role binaries + `rimsky-entrypoint` under one image — `rimsky-entrypoint` runs all three roles (scheduler + supervisor + control-api) when given no command, or a single role when the container `command:` names one (`[rimsky-scheduler]` / `[rimsky-supervisor]` / `[rimsky-control-api]`); an unknown role argument exits non-zero. Backend (postgres|sqlite) is selected by config — `dockerfiles/Dockerfile.rimsky`), `rimsky-all-in-one` (the `rimsky` image plus baked zero-config SQLite defaults so it runs out of the box for local dev — built `FROM rimsky:$(RIMSKY_IMAGE_TAG)` locally, i.e. this run's own rimsky image, and `FROM $(REGISTRY)/rimsky:$(VERSION)` on the push path; run with no command, so it spawns all three roles; it must follow the `rimsky` build — `dockerfiles/Dockerfile.all-in-one`, baking `dockerfiles/all-in-one.rimsky.yml`, whose `supervisor:` section carries the single-container supervisor tuning), `rimsky-host-daemon-proxy` (`dockerfiles/Dockerfile.go-base`), and `rimsky-conformance` (the protocol conformance runners, now `rimsky conformance <protocol>` subcommands shipped in the `rimsky` binary — the image runs `rimsky conformance …` — `dockerfiles/Dockerfile.conformance`). `make service-images` builds the eleven bundled-service images. Every local image build (`core-images` / `service-images` / `test-images`) tags each image with this run's per-run tag `:run-<12 hex>` alongside `:$(VERSION)` and `:latest`, and labels it `org.rimsky.project=rimsky-core`. The tag comes from `.ok-workspaces/bin/run-tag`, the ok-workspaces script the profile declares (`.ok-workspaces/config.json`, `runTag.path`); it prints a fresh value on every call, and one `make` invocation mints exactly one. Override it by exporting `env:RIMSKY_IMAGE_TAG` — that is how a build and a separate test process share one run's images. `:latest` is for interactive local dev only — the test harnesses no longer consume it. `make reap-images` prunes every rimsky-labeled image older than `REAP_HOURS` (default 72) by age alone, then prunes dangling labeled layers. `make push-images` publishes every tag as a multi-platform index (`linux/amd64` + `linux/arm64`) and `make verify-published-platforms`, the release chain's closing step, reads each pushed tag's platform list back from the registry. The CLI ships as a binary (`make cli`), not an image.

**Release flow** — see `RELEASING.md`. For formal releases, the `/release` skill (project-local at `.claude/skills/release/`) drives SemVer judgment, release-notes drafting + review, and the outward push chain through a single confirmation gate. For pre-release / dev builds, `make dev-release` runs the same build + scan + push chain mechanically — version derived as `v<next-minor>.0-dev.<date>.g<sha>` (SHA dot-joined into the SemVer pre-release segment, not `+gSHA` build metadata — `+` is invalid in Docker tag grammar, stripped by `npm version`, and rejected by `go get`), no notes, floating `:dev` Hub tag, npm `--tag dev`. Both paths share the extended `make release` chain (`lint → core-images → service-images → test-all → scan → push-images → verify-published-platforms`; `lint` includes `license-lint`, which also runs on every plain `make lint`, not just release). The chain's `push-images` step uses `docker buildx build --push --platform linux/amd64,linux/arm64 --provenance=mode=max --sbom=true`, so every published tag is a multi-platform index for Intel and ARM and carries SBOM + provenance attestations. `rimsky` is pushed before `rimsky-all-in-one`, which builds `FROM` it and must resolve it as an index. The closing `verify-published-platforms` step reads each pushed tag's platform list back from the registry with `docker buildx imagetools inspect` and fails the release on a tag carrying one platform. Refuses to run from a dirty tree.

**Recent changes** — `git log`. This repo keeps no CHANGELOG; design rationale lives in the concept catalog (above) and `.ok-planner/` history.

**Project records, out of context by default** — `.ok-planner/{specs,sketches,history}/`. Committed, versioned parts of the project, but **not the source of truth** (the source code and the whole `.ok-planner/design/` corpus — concepts, decisions, stories — are) and **not to be pulled into context unprompted**. `sketches/` is pre-spec, speculative future thinking (written by `/sketch`; archived per-file when taken up or abandoned); `history/` holds a same-named archive folder per artifact kind (`specs/`, `sketches/`, plus migrated pre-4.0 kinds `plans/`, `coverage/`, `tensions/`); everything under it is a past moment, preserved indefinitely, and reading either without a directing goal is context pollution when reasoning about the project as it stands. Read these only when a specific goal directs it. This is a context-discipline rule, **not** a commit rule — the files are committed and part of the project.

## Cross-cutting gotchas

These don't have a natural concept-doc home and would trip a fresh session.

- **Entrypoint role selection + the migrate story.** `rimsky-entrypoint` reads its single command argument: no command → run all three roles IN ONE PROCESS via `lib/control/launch` (the single-process all-in-one stack; this is one of several paths — alongside `rimsky compose run` and `rimsky run` in self-host mode — that set `env:RIMSKY_PROCESS_ROLE=unified`, which the roles read to place their metrics listeners and to decide whether the SQLite driver needs its shared-file warning); `command: [rimsky-scheduler|rimsky-supervisor|rimsky-control-api]` → spawn only that role binary as a child; anything else (unknown role, `rimsky-migrate`, or >1 arg) → exit non-zero with a clear error. Migrate runs synchronously before the roles start, but ONLY when this invocation owns it: the no-arg all-in-one path always migrates; a single-role container migrates only when the role is `rimsky-control-api` (so a three-container split migrates exactly once, not three racing runs and not never). Override with `env:RIMSKY_ENTRYPOINT_MIGRATE` — `=1` forces migrate (e.g. a dedicated one-shot init container), `=0` skips it; any other non-empty value (`true`, `yes`, a typo) is a startup error — the entrypoint exits non-zero naming the value.
- **Supervisor callback hostname.** The supervisor binds its async-callback HTTP listener on `0.0.0.0`, but executors need a reachable hostname to dial back. Set `cfg:supervisor.callback.advertise_host` — the `supervisor:` section of the unified configuration file, not a top-level `callback:` block, which the decoder ignores in silence — or `env:RIMSKY_SUPERVISOR_CALLBACK_ADVERTISE_HOST`, to a hostname the executors can reach the supervisor at. Empty advertise host + wildcard bind is now a STARTUP ERROR (the supervisor refuses to stamp `http://0.0.0.0` into callback URLs); an explicit non-wildcard `cfg:supervisor.callback.host` remains a legal advertise fallback. The per-run callback routes (`POST ${callback_url}/v1/runs/{run_id}/keepalive` and `/v1/runs/{run_id}/attributes`) require the dispatch's `cancel_token` as `Authorization: Bearer` — no token → 401.
- **Async-callback body shape.** An external executor must POST to `${callback_url}/v1/callback/{async_ack_id}` with an `AsyncCallbackBody` JSON body — exactly one of the `success` / `error` / `park` outcome keys. The `events` field is RESERVED (`reserved 1; reserved "events";` in the proto — a prior top-level field, now retired) and must not be sent; the Go supervisor's `json.Unmarshal`-based parse silently ignores it and any other unknown field rather than rejecting, so the conformance kit's callback receiver is the stricter of the two and rejects unknown top-level keys outright. The legacy `{type: "complete"|"blocked"|"errored"}` discriminator shape is GONE: the Go supervisor's callback handler rejects it (and any body without exactly one non-null outcome) with HTTP 400. See `proto:executor.proto::AsyncCallbackBody` for the wire shape.
- **Late-bound binaries must read `RIMSKY_DAEMON_PORT`.** When `rimsky-host-daemon` spawns a local binary as a late-bound service (`rimsky run --service <name>=<path>`), it picks a free port, sets `RIMSKY_DAEMON_PORT` in the child's environment, and poll-dials `127.0.0.1:<port>` until the child's gRPC server is up (bounded by the Spawn's ready-timeout). The spawned binary MUST read `RIMSKY_DAEMON_PORT` and bind its gRPC server there — there is no port handshake back to the daemon. A binary that ignores the env var or binds elsewhere fails the readiness poll and the dispatch returns `spawn_failed`. The proxy binary reads `RIMSKY_PROXY_GRPC_PORT` (default 8090, daemon-facing), `RIMSKY_CONTROL_API_URL`, `RIMSKY_CONTROL_API_TOKEN` (the cache-miss `GET /instances/{id}` fallback), and `RIMSKY_CONTROL_API_CA` (CA-bundle PEM verifying an HTTPS control API; CA set + non-HTTPS URL is a startup error). The proxy always runs two listeners: the daemon-facing one at `RIMSKY_PROXY_GRPC_PORT` carries the host-daemon protocol alone, and the service-facing one at `RIMSKY_PROXY_SERVICE_GRPC_PORT` (default 8091) carries the service protocols (executor, claim-producer, lifecycle, observability) — so a deployment points its executor and claim-producer entries at 8091, never 8090. Under `RIMSKY_SERVICE_AUTH=mtls` the proxy enrolls like every bundled service (via `lib/protocols/serviceauth`, renewing its leaf automatically) and the service-facing listener requires client certs from the deployment CA; with service-auth off it serves plaintext. The daemon-facing listener serves TLS in every posture: from the `RIMSKY_PROXY_TLS_CERT`/`RIMSKY_PROXY_TLS_KEY` keypair, else from the enrollment leaf, else from a leaf under a CA the proxy keeps for itself. It writes that CA's certificate to `env:RIMSKY_PROXY_LOCAL_CA_FILE` and its private key to the same path plus `.key` (mode 0600), and reuses both on the next start, so a restart serves leaves under the root every running daemon already pinned through `env:RIMSKY_DAEMON_TLS_CA`; with no path named it mints a fresh CA per process and every daemon must re-pin. The proxy re-issues the leaf from that CA before it expires, so the hop survives past the 24-hour leaf lifetime. The daemon's dial defaults to TLS; it verifies a pinned root against the fixed service server name when `RIMSKY_DAEMON_TLS_CA` names one, and against the system roots otherwise. Plaintext needs `RIMSKY_HOST_DAEMON_INSECURE` set on both ends (`rimsky daemon start --insecure` on the daemon side); the old opt-in `RIMSKY_DAEMON_TLS` and `--tls` are gone. NOTE: the proxy's source deliberately never contains the word "supervisor" (a pin test enforces routing stays blind to supervisor identity) — the deployment-side listener is named "service-facing" for that reason. `RIMSKY_CONTROL_API_URL` is also mandatory for daemon registration: the proxy verifies `Register.api_key` (the daemon's api-key **plaintext**, i.e. `RIMSKY_API_KEY` / `--api-key`, not the key id; or the `anonymous` sentinel) via `GET /v1/auth/whoami` and routes by the key id the control API reports — with no control-API URL the proxy fails closed and no daemon can register. See `concept:host-daemon` / `concept:host-daemon-proxy` for the architecture.
- **Shipped default ports come from two reserved blocks.** Ports 8080-8099 belong to rimsky's core listeners — control API 8080, supervisor async-callback 8081, host-daemon proxy daemon-facing 8090 and service-facing 8091 — and ports 9000-9199 belong to the bundled services. `code:lib/foundation/ports` holds the four core defaults and both block bounds; each bundled service declares its own as a `default<X>Port` constant the audit reads. Two fitness checks in `test/plumbline/default_ports_test.go` enforce it: every shipped default sits in its block and no two coincide, and each bundled image's `EXPOSE` set equals its binary's built-in defaults. A listener with no built-in default — a metrics endpoint, a claim producer's admin listener — takes its port from the operator and is declared nowhere. The supervisor's callback port defaults to 8081 when `cfg:supervisor.callback.port` is absent; an explicit `port: 0` still means "let the operating system assign one", which is what the CLI's self-host paths write.
- **Services integration harness resolves images by `RIMSKY_IMAGE_TAG` alone, never `:latest`.** The integration harness under `lib/services/test/` drives a real rimsky stack via testcontainers using **locally-built** images — nothing is fetched from a registry, and nothing is built inline at test time. Every image reference goes through `code:lib/services/test/harness/image_tag.go::ImageRef`, which reads `env:RIMSKY_IMAGE_TAG` and appends it: `<image>:$RIMSKY_IMAGE_TAG`. There is no fallback and no derivation — with the variable unset the harness fails loudly, naming the variable and the build command. A verification run therefore mints one tag, builds every image it verifies under that tag, and hands the tag to its suites, so a suite can only ever find an image that run built; staleness is unrepresentable, and a missing image fails naming the exact `<image>:run-<hash>` and the build command. `make test-all` and `make test-in-stack` mint the tag, build all three image sets, and export it. When running scenario/smoke tests directly via `go test`, do the same yourself: `export RIMSKY_IMAGE_TAG=$(.ok-workspaces/bin/run-tag) && make core-images service-images test-images`, then run `go test` in the same shell — otherwise the boot fails with that error. `make reap-images` cleans up accumulated `:run-*` tags. `make test-in-stack` is the in-network execution path: the host-side driver test (`lib/services/test/instackdriver`) boots a stack, then runs `rimsky-test/test-runner` — docker-stack test binaries `go test -c`-compiled from the same tree by `make test-images` — inside the stack's network; the runner container holds no docker socket and orchestrates nothing, and in-network suites (e.g. `lib/services/test/instack`) resolve the control API from `RIMSKY_TEST_STACK_BASE_URL` (unset → the suite boots its own stack host-side, so plain `go test` still works).
- **Claude-agent operator allowlists are namespaced env vars.** The bundled claude-agent executor (Go, `lib/services/executors/claude-agent/`) reads `RIMSKY_CLAUDE_AGENT_MCP_ALLOWLIST` and `RIMSKY_CLAUDE_AGENT_EXPOSE_ENV_ALLOWLIST` from its process env. Unset means open (zero-config local dev); set means an exact boundary — a node declaring an MCP server or expose-env name outside it fails that dispatch with an error naming the entry, instance, and node. Per-node declarations live in node config: `cli.mcp_servers` (inline-only, `transport: http | stdio | module`, with `http-loopback` an alias for `module`) and `cli.expose_env`.
- **Outbound-HTTP services block private egress by default (SSRF guard).** The `http-node` executor, the `verifier-http` executor, and the `sensor-http` sensor dial caller/template-supplied URLs through the shared `lib/services/internal/egress` guard: by default it **blocks** loopback/private/link-local (incl. the `169.254.169.254` cloud-metadata endpoint)/ULA/multicast destinations — checked on the resolved IP at connect time, so DNS-rebinding and redirect targets are covered too — and restricts the scheme to http/https. This is the opposite polarity from the claude-agent allowlists: unset = **closed**, not open. A deployment that legitimately reaches an internal HTTP endpoint (private IP) must opt that CIDR back in via `RIMSKY_EXECUTOR_HTTP_NODE_EGRESS_ALLOWLIST` / `RIMSKY_EXECUTOR_VERIFIER_HTTP_EGRESS_ALLOWLIST` / `RIMSKY_SENSOR_HTTP_EGRESS_ALLOWLIST` (comma-separated CIDRs/IPs, parsed fail-closed at startup). A malformed entry fails the service boot. In sensor-http only the poll client is guarded; the publish-to-control-API client is not (trusted, commonly private). The services harness sets the sensor allowlist so its `host.testcontainers.internal` poll works.

## Code style

Rimsky's coding methodology is **Plumbline** (`https://github.com/fallguyconsulting/plumbline`), consumed as a Claude Code plugin. Plumbline materializes `.claude/rules/plumbline-cheatsheet.md` into the repo as the per-session rules file — read that for the actionable rules. `.ok-plumbline/config.json` declares five citation tags. `@concept:`, `@story:`, and `@decision:` each resolve to a file under `.ok-planner/design/`; `@subject:` and `@practice:` resolve to `.ok-plumbline/subjects/<slug>.md` and `.ok-plumbline/practices/<slug>.md`. Both lint checks (`comment_hygiene` and `citation_resolution`) are enabled and run on every Edit/Write via a PostToolUse hook. A `@tag:` shape the config does not declare is residue from an earlier convention; delete it, or convert its load-bearing content into a name, type, assertion, or test per the cheatsheet.

Go specifics enforced by `.golangci.yml`: gofmt, goimports, govet, staticcheck, unused, ineffassign, errcheck, revive. Logging is stdlib `log/slog` only — no Zap, no Zerolog. HTTP routing is `go-chi/chi`. Postgres is `jackc/pgx/v5`. SQLite is `modernc.org/sqlite` (pure-Go, no CGO). Cron is `robfig/cron/v3`.
