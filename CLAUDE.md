# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Rimsky is a project-agnostic reactive node-graph orchestration platform. The codebase is organized into three Go modules plus a root layer split into `graph/` + `runtime/` + `control/` per the layer-crystallization design (`.ok-planner/specs/2026-05-04-layer-crystallization-design.md`), the 2026-05-12 nomenclature resolution (`.ok-planner/specs/2026-05-12-nomenclature-resolution-design.md`), and the 2026-05-13 four-layer restructure (foundation/integration → runtime; graph/executor → runtime/executor; graph/shared primitives → foundation/shared + foundation/cascade):

1. **Foundation** — `foundation/` (own Go module: `github.com/fallguy/rimsky/foundation`). Primitives only: cascade engine, claim/lock primitive types, persistence drivers (Postgres + SQLite), infrastructure shared types (`Clock`, `Logger`, `UUID`, `DeepMergeJSON` under `foundation/shared/`), state-machine enums (`NodeState`, `LastOutcome`, `ErrIllegalTransition` under `foundation/cascade/`), and persistable row-type primitives (`TemplateSpec`, `TemplateNodeDef`, `EvaluatorState`, `ErrorTypePolicy`, frame-resolution + resolve constants, `QualityRuleSpec`, `Severity` / `BackoffKind` / `JitterKind`, etc. under `foundation/spec/` — the data shapes; the graph algorithms that operate on them, e.g. `Evaluate`, `HoldingSubgraphsForTemplate`, `ValidateTemplate`, live in `graph/node/`). Self-contained: imports only `protocols/` + stdlib + minimal third-party. `cd foundation && go mod tidy` is clean.
2. **Protocols** — `protocols/` (own Go module: `github.com/fallguy/rimsky/protocols`). The three service-protocol Go interfaces (`ClaimProducer`, `Executor`, `LifecycleSubscriber`) plus the `.proto` sources and generated bindings. Stdlib + grpc + protobuf only.
3. **Graph** — `graph/` (root module). The cascade model: templates, instances, frame-resolution, scheduling, attributes, quality rules, node row types, graph-shared types specific to the cascade model (`Severity`, `BackoffKind`, `JitterKind`, `AccessKind`), and the scenario test harness. Imports `foundation` + `protocols`. One documented residual: `graph/scheduler/{scheduler.go,pure_cascade.go}` imports `runtime/` for the sweep entry points the scheduler tick orchestrates — flagged for separate follow-up; allowed in depguard via per-file exemption. `graph/scenario/` is also exempt because it boots the full stack for scenario tests.
4. **Runtime** — `runtime/` (root module). The bridge layer that consumes foundation primitives + graph types to execute. Hosts the supervisor runner (atomic acquisition tx, verify-before-run, callback server, terminal handler), the foundation tick sweeps (`SweepStaleHeartbeats`, `SweepOrphanedNodeRuns`, `SweepReady`, `SweepOrphanedClaimHandles`, `SweepParkedNodes`, `SweepOrphanedBlobs`), the auto-terminal mechanism, the unified terminal-decision engine (`ResolveClaimHandleTerminal`), the orphan-claim reaper, `runtime/remote/` (the only concrete gRPC client to ClaimProducer impls), and `runtime/executor/` (the executor gRPC client pool). Imports `foundation` + `graph` + `protocols`.
5. **Control** — `control/` (root module). Operator surfaces: `control/controlapi/`, `control/cli/`, `control/observability/` (discovery-cache, cascade-graph, metrics), `control/config/`. Imports `runtime` + `graph` + `foundation` + `protocols`. `control/` reads `graph/`; `graph/` never reads `control/` (enforced by `graph-purity` depguard rule, which subsumes the retired `graph-control-isolation` rule).

Plus `cmd/`, `stores/`, `executors/`, `sensors/`, `subscribers/`, `dashboards/` at the top of the consumption order: every reference binary under `cmd/`, bundled claim-producer reference impls under `stores/`, bundled executor reference impls under `executors/`, bundled sensors under `sensors/` (e.g. `sensors/sensor-cron/` owning cron firing after the 2026-05-15 plan B10 / D7 / E16 schedule-retirement cascade), bundled LifecycleSubscriber-protocol reference impls under `subscribers/` (e.g. `subscribers/openlineage/` for OpenLineage emission), and the operator dashboard under `dashboards/`.

Rimsky still ships as three independent long-running processes (`rimsky-scheduler`, `rimsky-supervisor`, `rimsky-control-api`) plus `rimsky-migrate`, `rimsky-executor-conformance`, `rimsky-conformance-probe`, `rimsky-claim-producer-conformance`. The three runtime processes communicate **only through Postgres** — they cannot import each other (enforced by depguard).

**ClaimProducers** (the protocol-layer name; "stores" is the bundled-services-layer colloquial term) are out-of-process standalone binaries that implement the gRPC ClaimProducer interface (`Open / Commit / Abandon / Release` + the `Capabilities()` startup handshake). The reference impls ship `filesystem` (concrete-paths only), `postgres` (regional access + items-table queue semantics implemented store-internally), and `stub` (in-memory test fixture). Rimsky talks to them via `runtime/remote/` — the only concrete `ClaimProducer` implementation in the rimsky module. Auto-terminal at holding-subgraph completion drives held-claim resolution: success → `Commit`; failure → `Abandon`; producer disposition (commit-vs-release-vs-delete on its own state) is governed by per-producer config.

**LifecycleSubscribers** are an opt-in second protocol on the same service binaries (configured via `protocols: [claim_producer, lifecycle_subscriber]` per service in `rimsky.yml`). The six methods (`OnTemplateRegistered/Deployed/Undeployed/Deregistered`, `OnInstanceCreated/Terminated`) are fired synchronously by control-api at state transitions; idempotency is tracked in `rimsky_lifecycle_idempotencies`.

**Executors** are services that speak the executor protocol (gRPC + HTTP+JSON bridge). Reference impls: `http-node` (Go), `claude-agent` (TypeScript / npm), `stub` (Go test fixture). Executors do **not** run in-process; supervisors dispatch to them over the wire.

Vocabulary: 1 graph-level message (`invalidate` — see `docs/concepts/invalidate.md`); recalculation is a scheduler action, not a service message. 5 node states (`fresh`, `stale`, `running`, `failed`, `parked`) plus a sibling `last_outcome` column for resolution flavor (`fresh_changed`, `fresh_unchanged`, `passed`, `pure_cascade`, `failed`). 3 declarable lifecycle handlers (`on_acquire_unavailable`, `on_executor_complete`, `on_executor_errored`) plus the `on_event` handler map for executor-emitted named events. 4 error actions (`retry`, `invalidate(targets)`, `give_up`, `pass`). Read `docs/concepts/` for the conceptual model and `.ok-planner/specs/2026-05-04-foundation-contract.md` + `.ok-planner/specs/2026-05-04-modeling-layer-contract.md` for the implementation shape before making non-trivial changes.

**Held vs. failed states.** `parked` is a non-terminal hold state distinct from `failed`. It is entered when an executor emits the `Park` terminal event and exits via either time-based wake (`SweepParkedNodes` processes `resume_at`), in-graph or admin invalidate, or watchdog timeout (`max_park_duration` → `failed` with `error_class: "park_timeout"`). Cascade does NOT propagate from `parked`; held claims are retained across the park boundary; the orphan-claim reaper skips `phase='parked'` rows because heartbeating is paused during park.

The three contracts in `.ok-planner/specs/` define the layered architecture's responsibilities:

- `.ok-planner/specs/2026-05-04-foundation-contract.md` — what foundation owns (cascade, claim/lock primitives, atomic acquisition, persistence drivers, sweeps).
- `.ok-planner/specs/2026-05-04-modeling-layer-contract.md` — what the root-module graph + control layers own (templates, instances, frames, scheduling, control-api, attributes, quality rules). Filename retains the pre-rename "modeling" slug; the substance is the post-2026-05-12 `graph/` + `control/` split.
- `.ok-planner/specs/2026-05-04-service-protocol-contract.md` — the three service-protocol protocols and their boundaries.

Earlier dated design docs in `.ok-planner/history/` capture the path here (stores redesign v2/v3, control-plane v1, frame-resolution, persistence-pluggable, layer crystallization). The contracts above supersede the earlier docs; the historical docs remain for context but are not authoritative.

## Package import rules (enforced; violations break the build)

These are non-negotiable. The repo is organized as **three Go modules** plus the graph + runtime + control layers at the root:

- **`foundation/`** — own Go module (`github.com/fallguy/rimsky/foundation`). Cascade engine + claim/lock primitives + persistence + shared infrastructure types. Depends on `protocols` + stdlib + minimal third-party (`pgx`, `uuid`, `modernc.org/sqlite`).
  - `foundation/cascade/` — node-state machine + cascade signal + state-machine enums (`NodeState`, `LastOutcome`, `ErrIllegalTransition`).
  - `foundation/locks/` — `ClaimProducer` interface (4 verbs + `Capabilities`), `ClaimID`/`ClaimSpec`/`NamedLockSpec`/`ClaimResult`/`Registry`/`NamedLocksConfig`, the `ModeCoexists` and `ScopesByteEqual` helpers, and the in-Go `storetest` fake.
  - `foundation/shared/` — infrastructure shared types: `Clock`, `Logger`, `UUID`, `DeepMergeJSON`, error helpers.
  - `foundation/spec/` — persistable row-type primitives: `TemplateSpec`, `TemplateNodeDef`, `NodeStoreRef`, `NodeLockRef`, `NodeAttributesDef`, `InheritEntry`, `EventHandler`, `HandlerInvalidate`, `OnAcquireUnavailable/Complete/TerminalHandler`, `ErrorTypePolicy`, `PolicyAction`, `EvaluatorState`, `ResolvedAction`, `QualityRuleSpec`/`Failure`/`EvalInput`, `Severity`, `BackoffKind`, `JitterKind`, frame-resolution + resolve constants, `SelfTarget`. Pure data — no algorithms. The graph algorithms that operate on these types (e.g. `Evaluate`, `HoldingSubgraphsForTemplate`, `ValidateTemplate`, `RequiredStores`) live in `graph/node/`.
  - `foundation/persistence/` — database protocol (`Database`, `AdvisoryLocker`, `Queue`, `Tables` umbrella, `ClaimHandleTable`, `ClaimHolderTable`, `FrameTable`, per-row-type `<RowKind>Table` interfaces) plus the postgres + sqlite impls. SQLite is dev-only; multi-host deployments require Postgres. (Adapter selector string `Config.Driver ∈ {"postgres","sqlite"}` is distinct from the runtime `Database` interface.)
  - `foundation/internal/` — private to foundation; graph, runtime, control, and bundled services CANNOT import (enforced by depguard `foundation-internal-isolation`).
  - `foundation/go.mod` is self-contained — no `replace` directive against the root module, no graph back-imports. `cd foundation && go mod tidy` is clean.
- **`protocols/`** — own Go module (`github.com/fallguy/rimsky/protocols`). Service-protocol Go interfaces + protobuf bindings. Stdlib + grpc + protobuf only. Proto sources at `protocols/proto/v1/`: `claim_producer.proto`, `lifecycle.proto`, `executor.proto`. Generated bindings under `protocols/proto/v1/gen/`.
- **Root module (`github.com/fallguy/rimsky`)** — graph layer + runtime layer + control layer + cmd binaries + bundled service reference impls. Imports `foundation` + `protocols` + stdlib.
  - `graph/` — graph-layer logic: `attribute/`, `template/canonical/`, `frame/`, `scheduler/`, `shared/` (graph-specific enums; `Severity`/`BackoffKind`/`JitterKind` alias into `foundation/spec`; `AccessKind`/`MessageType` are graph-only), `node/` (the row-type aliases re-export `foundation/spec` types; the algorithms — `Evaluate`, `HoldingSubgraphsForTemplate`, `ValidateTemplate`, `RequiredStores` — live here), `scenario/`. (The `qualityrule/` package retired in the 2026-05-15 data-platform-extensions plan P1; bundled verifier executors at `executors/verifier-shape-checks/` and `executors/verifier-http/` replace it.)
  - `runtime/` — bridge layer: supervisor runner, conductor, sweeps, orphan reapers, auto-terminal mechanism, terminal-decision engine, callback server, `remote/` (gRPC client to ClaimProducer impls), `executor/` (executor gRPC client pool).
  - `control/` — control-layer surfaces: `controlapi/`, `cli/`, `observability/`, `config/`.
  - `internal/pgtest/` — shared pgtest fixture (testcontainers-based Postgres harness) used by root-module tests across graph, runtime, and control.
  - `cmd/` — every reference binary (rimsky-control-api, rimsky-supervisor, rimsky-scheduler, rimsky-migrate, rimsky-executor-conformance, rimsky-conformance-probe, rimsky-claim-producer-conformance, rimsky-cli, rimsky-entrypoint).
  - `stores/` — bundled claim-producer reference impls (filesystem, postgres, stub) packaged as standalone binaries.
  - `executors/` — bundled executor reference impls (http-node, stub, claude-agent).
  - `dashboards/` — operator dashboard (`rimsky-dashboard`, TypeScript / Vite).
- **`go.work`** ties the three Go modules together for development.
- **`.golangci.yml` depguard** enforces five rules:
  - `pgx-isolation` — pgx allowed only in `foundation/persistence/postgres/`, `foundation/internal/pgtest/`, `cmd/`, `internal/pgtest/`, `graph/scenario/`, `stores/`, `test/smoke/`.
  - `foundation-internal-isolation` — only `foundation/` may import `foundation/internal/`.
  - `foundation-purity` — `foundation/` may not import `graph/`, `runtime/`, `control/`, `cmd/`, `stores/`, `executors/`, `dashboards/`. Applies unconditionally — there are no per-file exemptions. The persistable row-type primitives that `foundation/persistence` once reached for in `graph/node` now live in `foundation/spec/`.
  - `graph-purity` — `graph/` may not import `runtime/`, `control/`, `cmd/`, `stores/`, `executors/`, `dashboards/`. Per-file exemption: `graph/scheduler/{scheduler,pure_cascade}.go` may import `runtime/` for the sweep entry points the scheduler tick orchestrates. `graph/scenario/` is fully exempt because it boots the full stack for scenario tests.
  - `runtime-purity` — `runtime/` may not import `control/`, `cmd/`, `stores/`, `executors/`, `dashboards/`. (`runtime/` freely consumes `foundation/` + `graph/` + `protocols/`.)
  - The retired `graph-control-isolation` rule is subsumed by `graph-purity` (graph cannot import control under either name).

If you need to share logic between graph subsystems, it goes into `graph/shared/` (or `foundation/cascade/`/`foundation/locks/`/`foundation/shared/`/`foundation/spec/` if it's strictly foundation-level). Layer ordering: `foundation/` → `graph/` → `runtime/` → `control/`. Foundation is fully self-contained — no graph back-imports. One documented residual: `graph/scheduler` imports `runtime/` for sweep entry points the tick orchestrates (flagged for separate follow-up). `runtime/` is the bridge layer; it consumes `foundation/` + `graph/` + `protocols/` freely. `control/` reads `runtime/` + `graph/` + `foundation/`; nothing below `control/` reads `control/`.

## Blessed invariants (annotated `@blessed-invariant` in source)

These are load-bearing safety properties. Every one has a scenario test that exercises it; do not add idempotency short-circuits or "ergonomic" guards that would break them. Locations updated to post-Phase-6 paths:

1. **State machine rejects illegal transitions.** `running → running` under reason `dispatch_claimed` errors — it is **not** silently idempotent. (`foundation/cascade/state.go`)
2. **Node-run claim brackets the running window.** Lock-eligibility counts (e.g. named-lock `mode: counting`) come from `rimsky_node_runs.claimed_by IS NOT NULL` joined against `rimsky_claim_handles`. (`foundation/persistence/postgres/queue.go`)
3. **Multi-lock acquisition uses deterministic sorted order.** All locks (named, scope) acquired in the deterministic sort order to prevent deadlock under contention. (`runtime/runner_acquire.go`; `foundation/persistence/postgres/queue.go`)
4. **Claimant-guarded release.** Every `DELETE FROM rimsky_claim_handles` and every `UPDATE rimsky_node_runs SET claimed_by = NULL` is `AND … = supervisor_id`. Stale orphan sweeps cannot null or delete live ownership. (`foundation/persistence/postgres/queue.go`, `runtime/runner_acquire.go`, `runtime/orphan_reaper.go`)
5. **Verify-before-run.** Supervisor re-reads `claimed_by` immediately before calling the executor; bails as `orphaned_claim_lost_race` if ownership moved. (`runtime/runner_acquire.go`)
6. **Orphan-claim cutoff is `5 × heartbeat_interval`.** Same cutoff applies to `rimsky_claim_handles` orphan reap. (`runtime/conductor.go`, `runtime/orphan_reaper.go`)
7. **Advisory lock on scheduler tick.** Postgres uses `pg_try_advisory_lock(SCHEDULER_TICK_KEY)`; SQLite uses `sync.Mutex`. Skips the tick when another replica holds it. (`foundation/persistence/postgres/advisory_locker.go`, `foundation/persistence/sqlite/advisory_locker.go`)
8. **Session advisory lock on migrations.** Held for the duration of the batch; released at session close. Postgres uses `pg_advisory_lock`; SQLite uses an in-process mutex. (`foundation/persistence/migrations.go`, `foundation/persistence/postgres/advisory_locker.go`, `foundation/persistence/sqlite/advisory_locker.go`)
9a. **Lock state lives only in the persistence layer.** No claim-producer implementation persists lock state; `rimsky_claim_handles` is the sole authority. (`foundation/locks/interface.go` — on the `ClaimProducer` interface comment)
9b. **ClaimProducer implementations do not internally serialize on lock-shaped predicates.** The reader-lease serialization pattern is forbidden for `staged_async`; honest support requires snapshot delegation or native MVCC pass-through. (`foundation/locks/interface.go`)
4b. **Single-writer-per-scope; overlap is producer-defined, byte-equal as the trivial default.** The acquisition predicate rejects a new claim_handle row that conflicts with an existing held row for the same producer-claimed scope. Producers that advertise `SupportsScopesConflict: true` may define overlap via `ScopesConflict` (range-overlap, prefix-containment, MVCC snapshot overlap); producers that don't advertise default to byte-equal comparison of `rimsky_claim_handles.scope_data`. Either way, two writers cannot simultaneously hold the same logical scope. (`foundation/locks/interface.go`, `protocols/claimproducer/types.go::Capabilities`, `stores/stub/server/server.go`)
10. **Lock acquisition is atomic with parent-run claim acquisition.** The acquisition transaction either claims the parent run AND inserts the parent `rimsky_claim_handles` row AND inserts all sub-claim handle rows for opted-into partitioning (via `ClaimProducer.SplitScope`) AND records the `ClaimProducer.Open`-returned addresses, or none of these. The producer's own state mutations run in a producer-internal transaction decoupled from rimsky's. Single-writer-per-scope (invariant 4b) holds because rimsky's conflict predicate gates claim-handle INSERTs against `rimsky_claim_handles` only. (`runtime/runner.go`, `runtime/runner_acquire.go`, `runtime/runner_subclaim.go`, `runtime/supervisor.go`)
11. **Userdata is inert in Rimsky.** No code path inspects, parses, substitutes, or validates `userdata`. (`graph/attribute/substitution.go`; the `ExecuteRequest.userdata` proto comment)
12. **Attributes validate twice: at dispatch (post-substitution) and at commit (executor writeback).** Both gates mandatory. (`graph/attribute/validate.go`)
13. **Held-claim resolution is auto-terminal, single, and aggregate-outcome-driven.** At holding-subgraph completion (all `rimsky_claim_holders` rows in `'completed'` or `'failed'`), the supervisor fires exactly one resolution per held claim based on aggregate outcome: all-completed → Commit; any-failed → Abandon. The verb-fire-and-delete sequence is delegated to `ResolveClaimHandleTerminal` (the unified terminal-decision engine). (`runtime/auto_terminal.go`, `runtime/terminal_decision.go`)
15. **`Open` fires inside the rimsky-side acquisition transaction.** The supervisor's atomic acquisition transaction calls `ClaimProducer.Open` between the claim-handle row INSERT and the rimsky-side COMMIT. The producer's own state mutation runs in its own transaction (producer-internal, decoupled from rimsky's). (`runtime/runner_acquire.go`)
20. **Claim content (payload, address, scope) is inert in Rimsky.** Rimsky reads claim content by named-field path only at substitution-leaf extraction (`graph/attribute/substitution.go::walkPath`); does not log, validate, transform, normalize, decrypt, hash, index, pattern-match, attach to traces, include in errors, or otherwise act on claim content. Distinct from store-config bytes (operator-managed; not under invariant 20). Annotated at `foundation/locks/types.go` on `ClaimResult` and `graph/attribute/substitution.go::walkPath`.
21. **Blob content is inert in Rimsky.** Bytes spilled to a configured `BlobBackend` (per `persistence.blob.backend` ∈ {`inline` | `pg-largeobject` | `filesystem` | `memory`}) are read by rimsky only via the `walkPath` substitution path (the same exception that applies to inline attribute values and claim payload per invariants 11 and 20) and the persistence-layer fetch on attribute / parked-payload / named-event read. Rimsky never logs, formats with `%v`, validates beyond schema gates, transforms, normalizes, hashes, indexes, pattern-matches, attaches to traces, or includes blob bytes in error messages. Annotated at `foundation/persistence/blob.go` on the `BlobBackend` interface comment.
22. **Held-durable claim handles persist across instance dispatches.** A claim handle with `held_durable = true` is not deleted by holding-subgraph auto-terminal; only by explicit operator action (`DELETE /instances/{id}/assets/{alias}`) or instance termination (`ReleaseHeldDurableClaims`). The orphan-claim reaper skips `held_durable = true` rows. Recursive parent-claim resolution treats a held-durable child the same as a resolved-and-deleted child: it does not block the parent from firing its own auto-terminal. The child stays available for future co-holdership via `holds:` until explicit release. (`runtime/auto_terminal.go`, `runtime/instance_termination.go`, `runtime/orphan_reaper.go`)
23. **Exit-node writeback flows to parent run writeback.** For sub-graph parent runs, the exit node's terminal writeback is copied to the parent run's writeback row in the same transaction that records the exit's terminal. If the exit never runs (e.g., an internal node failed and strict-cancel killed exit before it dispatched), the parent's writeback stays empty. Per `@blessed-invariant 20` the bytes are round-tripped through `json.Marshal` for persistence-layer encoding but not transformed semantically. (`runtime/subgraph_dispatch.go::CarryExitWriteback`, `runtime/subgraph_dispatch.go::applyTerminalCompleteSubgraphExit`)
24. **Messages are inert in Rimsky.** Message payload bytes are read by rimsky only at two sanctioned sites: the substitution leaf in `graph/attribute/substitution.go::resolveTrigger` (via `walkPath` against the trigger message) and the persistence-layer fetch in `control/controlapi/messages.go::handleGetMessage` (which surfaces the row verbatim to the operator). Rimsky never logs, formats with `%v`, validates beyond schema gates, transforms, or includes payload bytes in error messages. Same opacity discipline as invariants 11/20/21. The message delivery path (`runtime/message_delivery.go`) touches envelope routing fields (kind, sender, sender_kind, target, frame_id, delivered_at) but never `payload`.

(Invariant 14 is retired post-v3.)

Scenario tests in `test/scenarios/` (e.g. `verify_before_run_race_test.go`, `state_machine_same_state_rejected_test.go`) and `test/scenarios/locks/`, `test/scenarios/stores/`, `test/scenarios/claim_stores/`, `test/scenarios/frame_resolution/`, `test/scenarios/lifecycle/` exist to catch regressions of these, plus the runner-level tests now co-located under `runtime/` (e.g. `runtime/runner_test.go`, `runtime/supervisor_test.go`, `runtime/auto_terminal_test.go`). When adding new invariant coverage, drive the supervisor through `graph/scenario.Start` against pre-launched producer-services on ephemeral ports (the smoke fixture in `test/smoke/setup.go` is the reference example).

## Build & test

The repo has three Go modules tied together by `go.work`. Standard commands:

```sh
make proto-gen        # regenerate proto bindings (run after editing protocols/proto/v1/*.proto)
make build-all        # go build across all three modules (root + foundation + protocols)
make test-all         # go test across all three modules
make lint             # golangci-lint (gofmt, goimports, govet, staticcheck, unused, ineffassign, errcheck, revive)
make tidy             # go mod tidy across all modules
```

Single-package or single-test runs:

```sh
go test ./runtime/...
go test ./test/scenarios/ -run TestVerifyBeforeRunRace -v
go test ./test/scenarios/... -count=5 -race      # flake hunt
```

**Scenario and storage integration tests use testcontainers-go to spin up a real Postgres** (`foundation/internal/pgtest/`, `internal/pgtest/`). They will pull the `postgres:14-alpine` or `postgres:15` image and require a working Docker socket — they are not unit-test fast. Each scenario boots its own container.

The TypeScript executor (`executors/claude-agent/`) has its own build:

```sh
cd executors/claude-agent
npm install
npm test                # vitest
npm run build           # tsc → dist/
```

## Schema (post-2026-05-15 data-platform-extensions)

- **`rimsky_node_runs`** — parent run-bookkeeping row. One per dispatched node-run. `phase` column drives the active+held lifecycle (`'pending' | 'active' | 'held' | 'parked' | 'completed'`). `claimed_by` carries the supervisor id while `phase='active'`. The orphan reaper covers `phase='active'` rows with stale heartbeat. Post-2026-05-15 the row carries the **run-tree** extension (`parent_run_id`, `child_key`, `aggregation_policy JSONB`) AND all state-bearing columns lifted from `rimsky_nodes` (`state`, `last_outcome`, `parked_reason`, `parked_reason_label`, `parked_resume_at`). State lives entirely here now.
- **`rimsky_nodes`** — declarative `(instance_id, template_node_alias)` row. State-bearing columns are GONE (lifted to `rimsky_node_runs`). Frame-end predicate re-roots to runs: "no `rimsky_node_runs` rows for this `frame_id` with `state` in (`stale`, `running`)."
- **`rimsky_claim_handles`** — child of `rimsky_node_runs` (FK with `ON DELETE SET NULL` so held claim handles outlive their parent's active terminal until auto-terminal fires). One row per (node_run, lock-or-claim acquired). `lock_kind` ∈ `{'named', 'scope'}`. `is_held BOOLEAN` marks claims that persist past active terminal. `realized_write_semantics` is the per-claim verdict from `ClaimProducer.Open`. Post-2026-05-15 carries `parent_claim_handle_id UUID NULL` (sub-claim chain), `lifetime TEXT NOT NULL` (`subgraph` | `durable`), `held_durable BOOLEAN NOT NULL` (persists past holding-subgraph completion), `version_id TEXT NULL` (DataProcessing canonical version), and `producer_candidate_handle BYTEA NULL` (opaque handle from `DataProcessing.BeginCandidate`).
- **`rimsky_claim_holders`** — held-claim subgraph state ledger. One row per (claim_handle, holder_run) for held subgraph members; `state` ∈ `{'active', 'completed', 'failed'}`. Auto-terminal fires when all rows for a claim_handle are non-active. The FK column is `claim_handle_id`. Post-2026-05-15 the holder key is `holder_run_id` (FK to `rimsky_node_runs.id`), not the legacy `holder_node_id` — holders are runs, not nodes.
- **`rimsky_lifecycle_idempotencies`** — per-(producer, scope_kind, scope_id) idempotency for LifecycleSubscriber events.
- **`rimsky_messages`** (new, 2026-05-15) — boundary-crossing message envelopes. Columns: `id`, `instance_id`, `kind` (V1: `invalidate`), `sender`, `sender_kind` (`operator | sensor | instance`), `target`, `payload`, `received_at`, `delivered_at`, `frame_id`, `cancelled`, `backfill_operation_id`. Delivered at frame boundary per per-instance `frame_delivery_mode` (`coalesce` default; `serial_queue` opt-in).
- **`rimsky_lineage`** (new, 2026-05-15; outcome column added 2026-05-16) — append-only lineage projection. Two `record_kind`s: `leaf_run` (per leaf-run terminal) and `claim_terminal` (per `ClaimProducer.{Commit,Abandon}` resolution; was `claim_commit` pre-2026-05-16). The per-row `outcome` column discriminates `claim_terminal` rows into `committed` / `abandoned` / `force_cancelled`. Source of truth is `rimsky_events` + `rimsky_claim_handles`; this is a materialized projection rebuildable from them.
- **`rimsky_sensor_watches`** (new, 2026-05-15) — rimsky-side watch state per `(sensor_name, watch_id)`. Columns include `instance_id`, `kind`, `resolved_config JSONB`, `on_observation JSONB`, `state` (`active | failed | stopped`).
- **`rimsky_schedules`** (dropped, 2026-05-15) — retired alongside the per-node `schedule:` template field and the scheduler-tick cron-fire path. Cron is now a sensor kind (`sensors/sensor-cron/`).

## Non-obvious gotchas

- **Two distinct callback hostnames.** The supervisor binds its async-callback HTTP listener on `0.0.0.0`, but executors need a service-reachable hostname to dial back. Set `callback.advertise_host` (YAML) or `RIMSKY_SUPERVISOR_CALLBACK_ADVERTISE_HOST` (env) to the supervisor's service name (compose) or Service DNS (k8s). Empty → executors can't reach back.
- **TS claude-agent async-callback path.** The executor must POST to `${callback_url}/v1/callback/{async_ack_id}` with body keyed `type` (not `kind`) — enforced by the Go supervisor's chi route. End-to-end test in `executors/claude-agent/src/server.test.ts`.
- **`changed: bool` is producer-declared, not content-hashed.** A node committing `changed: false` stops cascade propagation at itself; rimsky does not verify the claim. Trust + audit log, not hash-and-check.
- **Cron firing is owned by `sensors/sensor-cron/`** post-2026-05-15 schedule-retirement cascade. The bundled `sensor-cron` advances its own next-fire-at state; missed fires are NOT backfilled by default (`missed_fires: drop`) — intentional. The retired per-node `schedule:` field is rejected at template registration; the `rimsky_schedules` table is dropped. (`sensors/sensor-cron/`)
- **Operator-originated invalidates do not preempt running work.** In-flight work always runs to its terminal state. Invalidates either enqueue a new frame (`serial_queue` mode) or join the pending coalesce row (`coalesce` mode).
- **Frames are the unit of cascade resolution.** Every `rimsky_node_runs` row carries `frame_id NOT NULL`. Frame-end is the SQL predicate "no `rimsky_node_runs` rows for this `frame_id` with `state` in (`stale`, `running`)" — post-2026-05-15 re-rooted from `rimsky_nodes` to `rimsky_node_runs` since state lives on runs now. At most one frame is `running` per instance.
- **Sub-graph entry-node absorption is structural, not conceptual.** A calling node carrying `delegate: <graph>` and the entry node of that sub-graph share runtime identity: same `rimsky_nodes` row, same executor, same parent run. Exit, by contrast, has its own row and runs as a child; its writeback flows to the parent via the carry-rule (`runtime/subgraph_dispatch.go::CarryExitWriteback`). The asymmetry is load-bearing — don't try to give entry its own row.
- **Held-durable claim handles persist past holding-subgraph completion** (`@blessed-invariant 22`). The orphan-claim reaper skips `held_durable = true` rows; recursive parent-claim resolution treats held-durable children as resolved. Release is via explicit operator action (`DELETE /instances/{id}/assets/{alias}`) or instance termination only.
- **`strict.cancel_siblings: true` is supervisor-scoped.** The proactive sibling-cancellation walk (`runtime/terminal_decision.go::cancelInFlightSiblings`) filters mismatched-supervisor siblings out per `@blessed-invariant 4` (claimant-guarded release). Under multi-supervisor deployments (replicas > 1) where sub-claims of the same parent are acquired by different supervisor processes, "fail fast" is honored within a supervisor only — cross-supervisor siblings continue to natural completion and contribute to the parent's aggregate via their natural Commit/Abandon. The producer side is protected: forcing an Abandon from supervisor A on a claim held by supervisor B would race with B's native verb and corrupt the producer's `claim_id`-keyed state. See `concept:cancel-siblings` for the full multi-supervisor consequence.
- **Frame-delivery mode per instance defaults to `coalesce`.** `serial_queue` is opt-in via `POST /instances {template, params, frame_delivery_mode: "serial_queue"}`. Operators wanting strict one-message-per-frame ordering must select serial_queue at instance creation; the default coalesces pending messages into a single frame.
- **Sensor watches are state on the rimsky side** (`rimsky_sensor_watches`). Sensor-side state can be reconstructed via `ListWatches` resync (rimsky compares its expected set against the sensor's reported set and re-issues `StartWatch` for any missing).
- **Per-node `schedule:` field retired.** Cron is now a sensor kind via the bundled `sensor-cron`. Templates wanting cron fires declare a sensor in the `sensors:` block targeting the node; the sensor pushes invalidate-kind messages at fire time.
- **Backfill cancellation in V1 only blocks future-enqueued work.** `POST /backfills/{op_id}/cancel` marks pending undelivered messages as cancelled (skipped at frame delivery); in-flight frames complete normally (no preemption).
- **DataProcessing-capable producers receive `BeginCandidate` at parent-acquisition time.** The `producer_candidate_handle` lives on the sub-claim row and threads into the leaf executor's `ExecuteRequest`. `CommitCandidate` fires at leaf terminal (success), `AbandonCandidate` on failure / strict-cancel / backfill-abort.
- **Messages are inert in rimsky** (`@blessed-invariant 24`). Message payload bytes are read only at the substitution leaf (`graph/attribute/substitution.go::resolveTrigger`) and the persistence-layer fetch (`control/controlapi/messages.go::handleGetMessage`). The delivery path (`runtime/message_delivery.go`) touches envelope routing fields but never `payload`.
- **Foundation `internal/` is private; depguard enforces.** Only `foundation/` may import `foundation/internal/`.
- **Node-run phase column drives lifecycle.** Respect active vs held distinction in any new scheduling code. The orphan reaper at the node-run level covers ONLY `phase='active'` rows; held claims are auto-terminal concern.
- **Held-claim handles outlive their node-run's active phase.** The `node_run_id` FK uses `ON DELETE SET NULL` (not CASCADE) so held claim handles survive the node-run's deletion until auto-terminal explicitly removes them via `ResolveClaimHandleTerminal`.
- **Userdata is never substituted or inspected by rimsky.** `{{...}}` directives only resolve inside the `attributes` schema's `properties[*].source` field; identical-looking text in `userdata` reaches the executor verbatim. Don't add a "convenience" substitution pass — `@blessed-invariant 11` forbids it.
- **Per-instance userdata overrides exist.** `POST /instances` accepts a `userdata_overrides` blob shaped `{by_executor: {<name>: {...}}, by_node: {<name>: {...}}}` that rimsky deep-merges into per-node userdata at dispatch time, ordered template → by_executor → by_node (most-specific wins). Stored on `rimsky_instances.userdata_overrides`. Validation at create-time inspects only routing-key names (executor / node) — never the fragment values, preserving invariant 11. The merge helper is `foundation/shared.DeepMergeJSON`; the dispatch-time entry is `runtime.applyUserdataOverrides`. Use cases live executor-side: synthetic-blocker scenarios, per-run trace artifacts, ad-hoc tuning.
- **Held-claim resolution fires from `runtime/auto_terminal.go::CheckAndFireResolution`** which delegates to the unified `ResolveClaimHandleTerminal`. At every node terminal in a held subgraph: locks the claim_handle row (SELECT … FOR UPDATE); checks whether all claim-holders rows are non-active; if so, computes aggregate outcome (any failed → Abandon; else Commit); the engine fires the verb and deletes the row claimant-guarded.
- **Claim content is inert in Rimsky (blessed invariant 20).** Address, payload, and scope from `ClaimResult` are opaque `json.RawMessage` bytes from Rimsky's perspective. Don't `slog.Any("payload", ...)` or `%+v`-format any of these fields anywhere; don't include them in error messages; don't attach to spans or events.
- **ClaimProducers are out-of-process.** Reference impls live as standalone binaries under `stores/<kind>/` (filesystem, postgres, stub). Rimsky talks to them via gRPC through `runtime/remote/` — the only concrete `ClaimProducer` impl in the rimsky module. Each rimsky verb takes a `claim_id` (rimsky-generated UUID, also the claim_handle row id) so producers can correlate state across verbs.
- **Scope conflict is byte-equal.** Rimsky compares `rimsky_claim_handles.scope_data` byte-for-byte; producers canonicalize scope bytes such that two claims that should conflict produce byte-equal scopes. The standard filesystem store is concrete-paths only.
- **Atomicity is decoupled** between rimsky's bookkeeping tx and the producer's tx. Rimsky opens a tx, claims the node-run, INSERTs claim_handle rows, RPCs `ClaimProducer.Open` (the producer runs in its own tx), UPDATEs claim_handle addresses, INSERTs claim-holders, COMMITs. Failures on either side are recovered via the orphan reaper (rimsky-side) and the producer's own TTL/sweep.
- **`POST /admin/scheduled-nodes/{node_id}/force-fire` is admin-only** — bypasses the cron next-fire calculation. The smoke fixture drives 100 sequential force-fires through it.
- **Stub mode is required for conformance runs of LLM-calling executors.** `rimsky-executor-conformance --require-stub-mode` issues a probe via `rimsky-conformance-probe` at startup; non-stubbed executors will fail.
- **Templates are content-addressed.** `rimsky_templates.id` is `sha256-<64-hex>` over an RFC 8785 JCS-canonicalized spec (`graph/template/canonical/CanonicalSpecHash`). Tags in `rimsky_template_tags` are movable aliases. Re-registering the same spec is a cheap no-op. Pre-v1: hash bytes are not pinned across breaking changes — dev-DB nuke.
- **Lifecycle events fire from control-api, not the supervisor.** The six events are RPCed synchronously by control-api at state transitions; idempotency tracked in `rimsky_lifecycle_idempotencies`.
- **LifecycleSubscriber is an opt-in protocol.** Peers declare `protocols: [claim_producer, lifecycle_subscriber]` in `rimsky.yml`; bundled producer binaries can ship a no-op LifecycleSubscriber via `enable_lifecycle: true` config without forking the binary. Peers referenced by a template but not subscribed silently skip fan-out.
- **Instances bind to `template_hash` at creation.** FK is `template_hash TEXT`. `instance_key` (formerly `consumer_key`) is nullable. The instance HTTP create body is `{template, instance_key?, params}`.
- **Compose owns project-prefixed names.** Tags `compose:<project>:<...>` and instance keys `compose:<project>:<...>` are reserved for `rimsky-cli compose`. The CLI rejects manual registration with this prefix client-side.
- **`rimsky-cli` is a thin client; v1 does not version the control-api.** Bare paths (no `/v1/` prefix); rolling upgrades are operator-managed.
- **`RIMSKY_DB_URL` is gone.** All persistence config lives under the `persistence:` block in `RIMSKY_CONFIG` (`deploy/rimsky.yml`).
- **SQLite is the dev-only driver.** Multi-process / multi-host SQLite is not supported. Production deployments must use the postgres driver.
- **The unified image (`rimsky/all`) defaults to `driver: sqlite`** with state at `/var/lib/rimsky/state.db`. Running with replicas > 1 creates independent SQLite databases — broken. Use the per-process images plus the postgres driver for multi-replica deployments.
- **YAML config: `claim_producers:` block (legacy alias `stores:`).** Each entry has optional `protocols: [...]` (default `[claim_producer]`); required `write_semantics_allowed: [...]`. Legacy `write_semantics:` shortcut and `write_semantics_envelope:` name are both rejected at startup with a precise error. Operator's declared allowed set MUST be ⊆ producer's advertised allowed set (validated at startup).
- **Cascade-firing gate is `last_outcome == fresh_changed`, not `t.Changed`.** The supervisor's terminal-complete path now reads the resolved `last_outcome` (computed from the node's `on_executor_complete` handler resolution) before firing `cascadeChildrenStaleInTx` and `fanoutRecalculate`. Functionally identical to today's behavior under the default `by_changed` resolution; diverges under explicit `always_propagate` (force fresh_changed even on `changed:false`) and `never_propagate` (force fresh_unchanged even on `changed:true`). See spec `.ok-planner/specs/2026-05-05-reactive-loops-and-lifecycle-handlers-design.md`.
- **`pass` and `error` resolutions on `on_acquire_unavailable` / `on_executor_errored` call `Abandon`** on already-Open'd claims (matching `handleOrphanedClaim` semantics). Fired before the state-transition tx; producer-side state is cleaned up first. Per-emit invalidate frame discipline (`frame: in | next`) on every invalidate emit declaration: operator-API, error_types policy, lifecycle-handler. Default empty → `next`.
- **`frame_timeout_ms` measures "no progress in window," not frame age — and is purely advisory.** The scheduler tick emits a single `frame.stuck.observed` slog warning when `last_progress_at` (refreshed by every node-state transition write) falls outside the timeout, then takes no destructive action: the frame stays `running`, no nodes are failed, the instance is not terminated. A progressing self-invalidate loop stays under the timeout indefinitely; a wedged frame trips the warning. Pre-v1 design choice: no blanket "frame too old; kill it" policy.
- **Memory blob backend is dev-only.** Rejected at startup unless `RIMSKY_PROCESS_ROLE=unified` (set by `rimsky-entrypoint`); the per-process binaries (`rimsky-scheduler`, `rimsky-supervisor`, `rimsky-control-api`) cannot share state through an in-process map. The reject gate lives in `foundation/persistence/blob_config.go::ValidateBlobConfig`. Same caveat-class as SQLite-only-for-dev.
- **Parked nodes do not heartbeat.** The orphan-claim reaper skips `phase='parked'` rows because heartbeating is paused during park. Held claims persist across the park boundary; the auto-terminal mechanism still fires correctly when the parked node eventually completes or fails.
- **Event payloads are inert in rimsky.** Same opacity discipline as attribute values and claim payload (`@blessed-invariant 21`): bytes are read only via `walkPath` substitution and the persistence-layer fetch on attribute / event read; never logged, formatted with `%v`, validated beyond schema gates, transformed, attached to traces, or included in error messages.
- **`on_event` handlers are validated at template registration against the executor's `Capabilities.declared_events`.** When the executor's capabilities are not visible at registration time (service unreachable), the cross-check is skipped silently — runtime treats unknown event names as no-ops.

## Code style

Follow the cold-read conventions in `.claude/rules/cold-read-cheatsheet.md` (organize by feature not layer; ~500-line file / ~100-line function guideline; max 3 levels of nesting via early returns; prefer tracked duplication over hidden coupling; `@source:` / `@diverged:` annotations for copies; `@agent-contract` / `@blessed-invariant` blocks for stable cross-cutting concerns).

Go specifics enforced by `.golangci.yml`: gofmt, goimports, govet, staticcheck, unused, ineffassign, errcheck, revive (without the `exported` rule). Logging is stdlib `log/slog`, JSON output, field-structured — no Zap, no Zerolog. HTTP routing is `go-chi/chi`. Postgres is `jackc/pgx/v5`. SQLite is `modernc.org/sqlite` (pure-Go, no CGO). Cron parsing is `robfig/cron/v3`.
