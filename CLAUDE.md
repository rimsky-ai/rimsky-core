# CLAUDE.md

Rimsky is a project-agnostic reactive node-graph orchestration platform. This file is a pointer index — per rimsky's own "After Code Changes" rule, keep CLAUDE.md lean and only update it when something a future session would otherwise trip over has changed.

## Where to look first

**Architecture, concepts, invariants** — `.ok-planner/design/concepts.md` is the TOC; per-noun definitions, boundaries, and invariants live under `.ok-planner/design/concepts/<slug>.md`. The concept catalog is the durable design surface, updated alongside code through `/execute-plan` runs, and is the authoritative source for ownership and invariants. Start with `concepts/module-layout.md` for the four-module / four-layer split: the repo root holds four idiomatic top-level code directories — `cmd/` (binaries), `lib/` (shippable library code), `test/` (out-of-tree tests + their machinery), `tools/` (dev tooling). Library packages live under `lib/` (`lib/protocols`, `lib/foundation`, `lib/services`, plus the root-module `lib/graph` → `lib/runtime` → `lib/control` layer ordering); `lib/services` holds the bundled consumption-side services (claim_producers, sensors, subscribers, executors) shipped as images, isolated from core internals (it requires only `lib/protocols`); test scaffolding lives under `test/support/`.

**Enforced import boundaries** — `.golangci.yml` `depguard` block (`pgx-isolation`, `foundation-internal-isolation`, `protocols-purity`, `foundation-purity`, `graph-purity`, `runtime-purity`, `consumption-side-isolation`). If lint and prose disagree, lint wins. `go.work` ties the four Go modules together (root, `lib/foundation`, `lib/protocols`, `lib/services`).

**Load-bearing safety properties** — documented inside the relevant concept doc under `.ok-planner/design/concepts/<slug>.md` (each concept's Invariants section names them by id) and enforced by scenario tests under `test/scenarios/`. There is no in-code or in-prose tag form; the concept doc is the registry, the scenario test is the proof.

**Concept-to-code links** — `grep -rn '@concept:' .` in source.

**Open / unresolved design questions** — `.ok-planner/design/tensions/`.

**Build commands** — `Makefile`. Standard targets: `make build-all`, `make test-all`, `make lint`, `make tidy`, `make proto-gen`. `make build-all` / `test-all` / `lint` now also cover the `lib/services` module. `make service-images` builds the bundled-service images (one per claim_producer / sensor / subscriber / executor under `lib/services/`). Scenario and storage tests under `test/scenarios/...` and `lib/foundation/persistence/...` use testcontainers-go and require a working Docker socket.

**Public docs** — not part of this repo. This tree carries no docs sources, no docs-lint tooling, and no docs gate.

**Image builds** — Dockerfiles live in `dockerfiles/` (core) and co-located with each service under `lib/services/`. `make core-images` builds the four distributed core images: `rimsky` (all role binaries + `rimsky-entrypoint` under one image — `rimsky-entrypoint` runs all three roles (scheduler + supervisor + control-api) when given no command, or a single role when the container `command:` names one (`[rimsky-scheduler]` / `[rimsky-supervisor]` / `[rimsky-control-api]`); an unknown role argument exits non-zero. Backend (postgres|sqlite) is selected by config — `dockerfiles/Dockerfile.rimsky`), `rimsky-all-in-one` (the `rimsky` image plus baked zero-config SQLite defaults so it runs out of the box for local dev — built `FROM rimsky:$(VERSION)` and run with no command, so it spawns all three roles; it must follow the `rimsky` build — `dockerfiles/Dockerfile.all-in-one`, baking `dockerfiles/all-in-one.{rimsky,supervisor-config}.yml`), `rimsky-host-agent-proxy` (`dockerfiles/Dockerfile.go-base`), and `rimsky-conformance` (the protocol conformance runners, now `rimsky conformance <protocol>` subcommands shipped in the `rimsky` binary — the image runs `rimsky conformance …` — `dockerfiles/Dockerfile.conformance`). `make service-images` builds the eleven bundled-service images. The CLI ships as a binary (`make cli`), not an image.

**Release flow** — see `RELEASING.md`. For formal releases, the `/release` skill (project-local at `.claude/skills/release/`) drives SemVer judgment, release-notes drafting + review, and the outward push chain through a single confirmation gate. For pre-release / dev builds, `make dev-release` runs the same build + scan + push chain mechanically — version derived as `v<next-minor>.0-dev.<date>.g<sha>` (SHA dot-joined into the SemVer pre-release segment, not `+gSHA` build metadata — `+` is invalid in Docker tag grammar, stripped by `npm version`, and rejected by `go get`), no notes, floating `:dev` Hub tag, npm `--tag dev`. Both paths share the extended `make release` chain (`lint → license-lint → test-all → core-images → service-images → scan → push-images`). The chain's `push-images` step uses `docker buildx build --push --provenance=mode=max --sbom=true` so SBOM + provenance attestations land on Hub. Refuses to run from a dirty tree.

**Recent changes** — `git log`. This repo keeps no CHANGELOG; design rationale lives in the concept catalog (above) and `.ok-planner/` history.

**Project records, out of context by default** — `.ok-planner/{specs,plans,sketches,history}/`. Committed, versioned parts of the project, but **not the source of truth** (the source code and `.ok-planner/design/concepts/` are) and **not to be pulled into context unprompted**. `history/` (archived specs and plans) is a past moment and `sketches/` a speculative or in-progress future; reading either without a directing goal is context pollution when reasoning about the project as it stands. Read them only when a specific goal directs it (e.g. `/brainstorm` consulting a relevant sketch or prior plan). This is a context-discipline rule, **not** a commit rule — the files are committed and part of the project; some sketches are temporary planning input removed after use, which is also fine.

## Cross-cutting gotchas

These don't have a natural concept-doc home and would trip a fresh session.

- **Entrypoint role selection + the migrate story.** `rimsky-entrypoint` reads its single command argument: no command → run all three roles IN ONE PROCESS via `lib/control/launch` (the single-process all-in-one stack; this path alone sets `env:RIMSKY_PROCESS_ROLE=unified`, which gates the memory blob backend — `cfg:persistence.blob.backend` = "memory" is legal only here, because per-role processes cannot share the in-process map); `command: [rimsky-scheduler|rimsky-supervisor|rimsky-control-api]` → spawn only that role binary as a child; anything else (unknown role, `rimsky-migrate`, or >1 arg) → exit non-zero with a clear error. Migrate runs synchronously before the roles start, but ONLY when this invocation owns it: the no-arg all-in-one path always migrates; a single-role container migrates only when the role is `rimsky-control-api` (so a three-container split migrates exactly once, not three racing runs and not never). Override with `env:RIMSKY_ENTRYPOINT_MIGRATE` — `=1` forces migrate (e.g. a dedicated one-shot init container), `=0` skips it; any other non-empty value (`true`, `yes`, a typo) is a startup error — the entrypoint exits non-zero naming the value.
- **Supervisor callback hostname.** The supervisor binds its async-callback HTTP listener on `0.0.0.0`, but executors need a reachable hostname to dial back. Set `callback.advertise_host` in YAML or `RIMSKY_SUPERVISOR_CALLBACK_ADVERTISE_HOST` env to a hostname the executors can reach the supervisor at. Empty → executors can't reach back.
- **Async-callback body shape.** An external executor must POST to `${callback_url}/v1/callback/{async_ack_id}` with an `AsyncCallbackBody` JSON body — exactly one of the `success` / `error` / `park` outcome keys (plus an optional `events` array). The legacy `{type: "complete"|"blocked"|"errored"}` discriminator shape is GONE: the Go supervisor's callback handler rejects it (and any body without exactly one outcome) with HTTP 400. See `proto:executor.proto::AsyncCallbackBody` for the wire shape.
- **Late-bound binaries must read `RIMSKY_AGENT_PORT`.** When `rimsky-host-agent` spawns a local binary as a late-bound service (`rimsky run --service <name>=<path>`), it picks a free port, sets `RIMSKY_AGENT_PORT` in the child's environment, and poll-dials `127.0.0.1:<port>` until the child's gRPC server is up (bounded by the Spawn's ready-timeout). The spawned binary MUST read `RIMSKY_AGENT_PORT` and bind its gRPC server there — there is no port handshake back to the agent. A binary that ignores the env var or binds elsewhere fails the readiness poll and the dispatch returns `spawn_failed`. The proxy binary reads `RIMSKY_PROXY_GRPC_PORT` (default 9090), `RIMSKY_CONTROL_API_URL`, and `RIMSKY_CONTROL_API_TOKEN` (the cache-miss `GET /instances/{id}` fallback). See `concept:host-agent` / `concept:host-agent-proxy` for the architecture.
- **Services integration harness consumes locally-built images.** The integration harness under `lib/services/test/` drives a real rimsky stack via testcontainers and pulls **locally-built** image tags — nothing is fetched from a registry. `make test-all` builds `core-images` + `service-images` first as prerequisites, so its docker-stack suites always prove the current source (a stale local image would silently wave regressions through). When running scenario/smoke tests directly via `go test` (bypassing make), run `make core-images && make service-images` yourself first — otherwise the harness exercises a stale image, or fails when testcontainers can't find the tag locally.
- **Claude-agent operator allowlists are namespaced env vars.** The bundled claude-agent executor (Go, `lib/services/executors/claude-agent/`) reads `RIMSKY_CLAUDE_AGENT_MCP_ALLOWLIST` and `RIMSKY_CLAUDE_AGENT_EXPOSE_ENV_ALLOWLIST` from its process env. Unset means open (zero-config local dev); set means an exact boundary — a node declaring an MCP server or expose-env name outside it fails that dispatch with an error naming the entry, instance, and node. Per-node declarations live in node config: `cli.mcp_servers` (inline-only, `transport: http | stdio | module`, with `http-loopback` an alias for `module`) and `cli.expose_env`.

## Code style

Rimsky's coding methodology is **Plumbline** (`https://github.com/fallguyconsulting/plumbline`), consumed as a Claude Code plugin. Plumbline materializes `.claude/rules/plumbline-cheatsheet.md` into the repo as the per-session rules file — read that for the actionable rules. The only configured citation tags are the three declared in `.plumbline.json`: `@concept:`, `@story:`, `@decision:` — each resolves to a file under `.ok-planner/design/`. Both lint checks (`comment_hygiene` and `citation_resolution`) are enabled and run on every Edit/Write via a PostToolUse hook. Any other `@tag:` shape that survives in source is residue from an earlier convention; delete it, or convert its load-bearing content into a name, type, assertion, or test per the cheatsheet.

Go specifics enforced by `.golangci.yml`: gofmt, goimports, govet, staticcheck, unused, ineffassign, errcheck, revive. Logging is stdlib `log/slog` only — no Zap, no Zerolog. HTTP routing is `go-chi/chi`. Postgres is `jackc/pgx/v5`. SQLite is `modernc.org/sqlite` (pure-Go, no CGO). Cron is `robfig/cron/v3`.
