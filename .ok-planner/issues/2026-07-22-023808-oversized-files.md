# Forty files blow past the size guideline nobody enforces — act, gate, or shrug?

Rimsky's house style guide recommends keeping files under roughly 500 lines — framed not as a readability rule but as merge-conflict insurance, because the project runs on parallel work in isolated git checkouts, and big files widen the odds that two people's changes collide. Forty-one files currently exceed 700 lines, several at 2–5× the guideline, topped by one 2,766-line test file. The guideline has never been enforced for any file: no lint rule, no CI gate, no baseline — aspirational prose only. The question is whether to act on the backlog, and how.

Re-verification confirmed the list (files grew slightly since filing, none shrank) and confirmed the design corpus is silent by design — its closest document explicitly disclaims ownership of file layout inside packages. This is a development-process call, not a design question the docs can settle. The uncomfortable irony shaping the options: the files most worth splitting are the large, frequently-touched ones — which are exactly the files where a dedicated splitting campaign would collide with in-flight work, causing the conflicts it's meant to prevent.

## Options

- **Opportunistic splits only** — carve along feature seams whenever a file is being touched anyway. No forced churn; but untouched hot files stay oversized indefinitely.
- **Leave it a guideline.** Honest about the status quo; answers nothing.
- **Baseline ratchet** — record current sizes, fail CI only on growth. Stops the bleeding without mandating cleanup; new tooling to build.
- **Dedicated splitting campaign.** Uniform fix, maximum churn, and the conflict risk lands on precisely the files in question.
- **Split test files on their own faster track** — several top offenders are tests, where splitting into sibling files risks no runtime behavior at all.

The ruling decides: act now or not; which mechanism (opportunistic, campaign, ratchet, or a combination); priorities; and whether tests run on a separate track.

## Ruling

> Recommended ruling (/recommend-rulings): Opportunistic feature-seam
> splits only, prioritized as filed (the sqlite/postgres nodes.go pair
> first, then auto_terminal_test.go), with test-file splitting as its
> own lower-friction track. No dedicated sprint and no enforcement
> tooling now.
>
> Rationale: A big-bang wave churns exactly the hot, frequently-
> touched files it targets, maximizing conflict with in-flight work —
> the very cost the issue is about. The ~500-line guideline is a
> granularity heuristic per Plumbline, not a gate; revisit enforcement
> only if worktree conflicts actually bite.
