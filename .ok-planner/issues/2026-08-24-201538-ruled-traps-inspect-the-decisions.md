# Forty traps that need the owner's review: 22 the corpus ruled, 18 whose fix changes product behavior or the corpus

## Problem

`/document` at release `d977250c` recorded 70 traps at `.ok-planner/documentation/traps/`. A trap is a belief a user plausibly forms from the public surface. An experiment contradicted each one. A triage on 2026-08-23 (`.ok-planner/workbench/2026-08-23-trap-triage.md`) read each trap against the design corpus. This issue holds two sets. For the 22 traps in the first table, a decision or concept states the measured behavior as a deliberate choice. The corpus made these traps. At each one the project chose against what a user expects.

The second set sits under the heading after the first table. It holds 18 traps the corpus is silent on. Each fix changes real product behavior, or contradicts or amends a design artifact. They moved here from `issue:silent-traps-align-to-user-expectation` on 2026-08-24, each with the planner's recommendation.

Each ruling in the first table needs a second look with the user's belief in hand. Each row asks one question: is the choice worth the surprise it causes, or should the belief win and the artifact change?

| trap | ruling artifact | what a user expects | why the artifact rules it |
| --- | --- | --- | --- |

## Silent traps whose fix changes product behavior or amends the corpus

The triage found no corpus text on these 18. On closer inspection each fix either changes real product behavior or contradicts or amends a design artifact, so they need the owner's review. Each row carries the planner's recommendation from the 2026-08-24 planning session.

### The fix would contradict or rewrite a corpus artifact

| trap | what it is, and why it surprises | recommendation | why |
| --- | --- | --- | --- |
| `attribute-defaults-have-per-node-form` | Instance-level attribute overrides come in per-executor and per-node forms. A template author expects `defaults.attributes.by_node` beside `defaults.attributes.by_executor`. The template side has only `by_executor`. `concept:attribute` enumerates exactly five override layers, with the template contributing one. | Add `defaults.attributes.by_node`. The template's two forms compose as one layer: executor name then node name, node winning — the order the instance side already uses. No `by_match` at template level. Amend `concept:attribute` so the template layer reads "per-executor then per-node defaults". | Mirrors the instance side. Five layers stay five. |
| `env-overrides-every-config-key` | A Kubernetes operator expects every `rimsky.yml` key to have a `RIMSKY_*` override, so no file needs mounting. Rimsky reads a fixed registered set. A guessed `RIMSKY_PERSISTENCE_DRIVER` changes nothing, silently. | Keep `decision:config-yaml-loading-policy` and `decision:env-var-registry` as they stand: no derived per-key overrides. `${VAR}` inside the file is the environment path. Add a decision saying so. The next row makes the guessed name a startup error instead. | Deriving names from key paths is the reflection-driven dispatch the plumbline rules forbid. It would double the registry. |
| `env-unknown-vars-rejected` | A misspelled YAML key stops the process and names the key. A misspelled `RIMSKY_*` variable is ignored without a word. | Every shipped binary checks its environment at startup: a `RIMSKY_*` name absent from the registry is a startup error naming the variable. The registry that `tools/env-registry` builds today only for the fitness test is embedded into the binaries. The check covers the whole registry, not per role, so all-in-one and split containers behave alike. Amend `decision:env-var-registry` to add the runtime check. | Same loud failure the YAML side already has. A hard error, not a warning, matches it. |
| `event-kinds-paired` | `lock_acquired` pairs with `lock_released`, so an operator expects `claim_acquired`/`claim_released` and `subclaim.acquired`/`subclaim.released`. Claim release is spelled `claim_resolution.commit`/`.abandon`. Subclaims have no release kind. `claim_held` returns the same rows as `claim_acquired`. | Rename to pairs: `claim.acquired`/`claim.released` (with a `resolution: commit\|abandon` field) and `subclaim.acquired`/`subclaim.released`, emitted where a subclaim resolves. Retire `claim_held`. Amend `decision:event-log-kind-enum` with the pairing rule: every acquisition kind has a release kind of the same stem. | Pre-v1, no compatibility is owed on event-log payloads. The rename is legal, and the vocabulary ends up regular. |
| `conformance-exit-code-machine-readable` | A CI author expects `rimsky conformance <protocol>` to exit differently for "a check failed" and "could not reach the endpoint", and to offer `--json`. Both exit 1 today, and there is no JSON. | Add `--json` to every conformance subcommand (the typed results slice, on stdout). Exit codes join the three-class scheme `decision:exit-codes` already sets for `rimsky run`/`compose run`: 0 pass, 1 a check failed, 2 could not run (endpoint unreachable, bad flags). Amend that decision to name the conformance family in scope. No new code number. | The decision's rejected alternative is a code per failure kind. "Could not run" is already its own class, so reachability fits without contradicting it. |
| `template-lint-equals-registration-validation` | An author expects `rimsky template lint` to catch offline everything registration rejects. It always dials the control API. Half the checks (executor and claim-producer names, expected-attribute schemas) come from live service handshakes that cannot exist offline. | `template lint` runs the structural checks in-process when no endpoint is reachable and prints every deployment-dependent check as `skipped: needs a deployment`, never as passed. With an endpoint it runs the full set as today. Amend `decision:template-registration-validation-unconditional`: registration stays unconditional, lint's offline subset is named, and every skip is printed. | Meets the belief as far as it can be met and keeps the decision's guarantee: a skip is loud, not a false pass. |
| `http-error-envelope-uniform` | A client author expects one JSON error envelope with a stable `code` on every non-2xx response. The control API has four shapes: core routes, observability, MCP, and chi's plain-text 404. | One envelope everywhere: `{"error":{"code","message","details"}}`, the shape `lib/control/observability/handler.go` already uses. Register JSON 404/405 handlers on the router. `POST /v1/mcp` keeps JSON-RPC's own error shape. Producer errors get `code: producer_error`, with class and producer name under `details`. Amend `decision:producer-error-passthrough` with that mapping. | Adopts the existing shape rather than a third one. The MCP exception is the spec's, not rimsky's. |
| `mcp-catalog-hides-denied-tools` | An agent with a narrow key expects `tools/list` to show only tools it can call. The catalog filters by action only. A tool the key holds under a scope is listed, then fails on out-of-scope resources. | Disclose rather than hide: the listed entry carries the grant's scope. Amend `concept:control-api`: the catalog filters by action grant and marks scoped grants on the entry. | Hiding would remove every scoped tool from every narrow key, including the resources it may call. Disclosure lets the agent check before calling. |
| `mcp-resource-uris-are-a-family` | The `rimsky://` scheme reads like a family. An agent expects instances, nodes, and events to be addressable as resources. Only two breakpoint-hit forms exist. | Add the instance-scoped family: `rimsky://instances`, `rimsky://instances/{id}`, and `/nodes`, `/frames`, `/events`, `/messages` under it. List the breakpoint form from `resources/list`. Templates, tags, and audit stay tools. Record a decision: MCP resources are the instance-scoped read family; everything else is a tool. Amend `concept:control-api` to name the family. | The belief names instances, nodes, events. The narrower family satisfies it without reproducing every REST noun. |
| `asset-verbs-match-across-surfaces` | An operator expects every asset operation on CLI, REST, and MCP alike. `rimsky asset lineage` has no route or tool. Materialization history has a route and tool but no CLI verb. | Add `rimsky asset materialization-history` over the existing route. Lineage stays a client-side composition of two reads. Amend `decision:asset-materialize-endpoint-retired` to say so, extending its enumeration. | The decision already retired a server-side convenience as sugar over existing reads. A lineage route is the same sugar. |
| `compose-restart-supervises` | `instances[].restart` reads like a container restart policy. An operator expects the runtime to recreate an instance that terminates. `restart` is applied only while `compose apply` runs. `compose status` still shows a dead instance as in-manifest. | Client-side: `rimsky compose up --watch` keeps reconciling on an interval while it runs. `compose status` shows terminated instances as terminated. Amend `story:compose-lifecycle` to say reconcile runs at apply and continuously under `--watch`. No server-side supervision. | Server-side restart would persist policy and add a scheduler watcher, a new runtime feature with no story behind it. |
| `egress-guard-on-every-outbound-service` | A security reviewer expects every bundled service dialing a supplied URL to sit behind the default-closed egress guard. The OpenLineage subscriber dials bare. claude-agent hands node-declared MCP server URLs to the `claude` CLI unchecked. | Wire the guard into the OpenLineage emitter with `RIMSKY_SUBSCRIBER_OPENLINEAGE_EGRESS_ALLOWLIST`. MCP server declarations stay outside the guard: amend `decision:destination-allowlists-default-closed` to say node-declared MCP servers are template-author-trusted, like the existing name allowlist. | Local MCP servers are loopback by design (`http-loopback` is a first-class transport). Guarding them would break zero-config local development. |
| `metrics-on-bundled-services` | The three core roles serve `/metrics` on a port. An operator expects the eleven bundled services to as well. None does. | Every bundled service serves `/metrics` (the existing promhttp pattern) when `RIMSKY_METRICS_HOST`/`RIMSKY_METRICS_PORT` are set — the generic variables the core roles read — with no shipped default port. Amend `decision:operator-env-namespaced-per-service` to place the metrics variables on the shared-infrastructure side, beside `RIMSKY_LOG_LEVEL`. | One service per container makes a generic name unambiguous. It matches how the log-level variable was made universal. |
| `park-controls-on-every-executor` | A template author expects `probe_park`, `probe_cancel`, and `park_resume_at` to work on any executor in production. They work on all four bundled executors now, but only under `RIMSKY_EXECUTOR_STUB_MODE=1`. | Nothing to build: amend `concept:parked-state`'s Boundaries to state the probe attributes are a conformance-testing contract, honored under stub mode, not a production attribute family. | A production park trigger is a new runtime feature with no story. The remaining surprise is documentary, and the concept can carry it. |

### The fix changes product behavior with no corpus text either way

| trap | what it is, and why it surprises | recommendation | why |
| --- | --- | --- | --- |
| `http-delete-idempotent` | A teardown script expects `DELETE` on an already-absent resource to succeed on every route. A second delete of a tag, instance, template, breakpoint, or asset answers 404. `auth revoke` of an unknown key name errors. | Every `DELETE` route answers its own success status on an absent target, and where the route has a body it says which happened: `"outcome": "deleted"` or `"absent"`. `auth revoke` keeps its body and gains `not_found` as a success outcome beside `already_revoked`. The 409 paths stay (instance not terminal, template still deployed, asset with holders). `DELETE /v1/mcp` is session teardown, not a resource, and stays. | Scripts get idempotence. The body keeps the signal an operator needs to notice a typo, so revoking a name that never existed is visible, not silent. |
| `http-events-streamable` | The CLI has `watch` and `--follow`, so an operator expects `GET /v1/events` to stream. The route is a finite page. `?follow` is silently ignored. The CLI's `--follow` is a client-side poll loop. | `GET /v1/events` gains a follow mode on `?follow=true` or `Accept: text/event-stream`: the handler holds the connection and emits each new matching event as a server-sent-events frame, polling the store on a short interval inside the handler. The CLI's `--follow` verbs and `rimsky watch` switch to it. Amend `concept:event-log` with the live-tail read. | SQLite has no change notification, so a push channel cannot be backend-neutral. Server-side polling gives one streaming contract on both backends with no new persistence plumbing. |
| `permission-actions-cover-full-crud` | An operator minting a scoped key expects every noun to carry its full verb set: `instance:update`, `asset:create`, `message:delete`. Those actions do not exist because the operations do not: nothing updates an instance, executors create assets, and messages are an append-only bus. | Build nothing. Record a decision that the action registry mirrors the operations that exist, naming the three absences and why: an instance changes through its attribute and lifecycle routes, an asset is produced by a node run, a message is immutable once delivered. `auth create` rejects an unknown action already and keeps doing so. | Inventing three operations to satisfy a naming symmetry is feature work with no story behind it. The decision makes the absence deliberate and documented. |
| `permission-wildcards-are-globs` | An operator expects grant wildcards to be ordinary globs (`instance:re*`). The grammar is three fixed shapes: `*`, `noun:*`, `*:verb`. Key creation accepts a wildcard whose noun or verb is unregistered (`banana:*`) without complaint. | Keep the three shapes. `ValidateGrantScope` rejects a wildcard whose noun or verb matches nothing in the registry, naming the entry, the way an unknown literal action is rejected today. Record a decision naming the grammar and rejecting infix globs. | An authorization matcher should be small and exact. An infix glob silently widens to verbs added later. The tightened check removes the silent half of the trap. |

## Candidates

- Reaffirm the ruling: the artifact stands, and the documentation carries the trap as a stated tradeoff.
- Overturn the ruling: the user's belief wins, the artifact is revised or retired through a sprint's corpus delta, and the behavior changes.
- Narrow the ruling: the artifact stands for the case it names and the trap's wider case is fixed.
