# v0.8.0 docs-reconcile source findings

Source: the rimsky-docs reconcile of the published corpus against the v0.8.0
release (2026-06-10/11). The reconcile's review loop verifies every doc claim
against this repo's code; the items below are the residue that could **not** be
fixed docs-side — each is a rimsky-core gap, bug, or code-comment drift. The
docs now describe the actual v0.8.0 behavior in every case, so fixing these
later will require a docs re-reconcile (`/update-docs` in rimsky-docs picks the
changes up automatically at the next release).

Grouped by weight: functional gaps first, then a suspected bug, then
comment/doc-string drift, then cosmetics.

## 1. Functional gaps (capability the wire contract or comments imply but the runtime doesn't deliver)

### 1.1 No template-level parallel N-way join

There is no template shape that makes a node dispatch only after **all N**
heterogeneous upstream siblings settle in the same wave. Traced behavior:

- The settlement cascade walks only direct subscribers of the emitted signal —
  the deeper BFS was deliberately retired
  (`lib/runtime/runner_terminal.go` ~905-915).
- A receiver's wait-set row is inserted at the settling sender's terminal and
  drained **in the same transaction** (insert-then-drain, ~716-723 +
  `drainWaitSetOnSettled` ~417). With parallel upstreams, the receiver is
  dispatch-eligible the moment the *first* upstream settles; whether it
  observes the others is a supervisor-timing race.
- The once-per-frame guard (`visitedReceivers` + `HasRunForNodeInFrame`,
  ~773-816) means the receiver fires exactly once per wave — but possibly
  *prematurely*, and it is never re-fired when stragglers settle.
- Pessimistic (genuinely blocking, undrained) wait-set inserts exist only on
  in-flight transitions: `lib/runtime/cascade_invalidate.go::invalidateInFrame`
  (~330-341), retry, heartbeat-lost, parked wake, hard-dep pulls.

The only parallel all-N barrier today is **fan-out** (parent settles only
after all partition children resolve). The docs' fan-in cookbook recipe was
restructured around a serial chain accordingly.

Also: the comments in
`test/scenarios/subscription_cascade_test.go`
(`TestSubscriptionCascade_EligibilityRespectsMultipleSenders`) describe
one-frame multi-sender gating that the test's assertions don't actually pin —
under `serial_queue` the three admin invalidates become three serial frames,
and the test asserts only final `fresh` states. Either the comments or the
assertions should change.

**Ask:** decide whether a template-declared N-input join is wanted pre-v1
(wait-set rows seeded for *all* matching upstreams at wave start, or a
`join:`/`barrier:` subscription attribute), or bless the serial-chain +
fan-out answer and say so in the design concepts.

### 1.2 `error_types:` cannot route producer-declared acquisition classes

The validator and the runtime disagree about who owns an acquisition error
class:

- `lib/graph/node/template_validator.go::validateErrorTypes` (~436-498)
  range-checks every `error_types:` key against the **node's executor's**
  `declared_error_classes` (only the `acquire/*` prefix plus a fixed exempt
  list passes).
- `lib/runtime/runner_lifecycle.go::handleAcquireUnavailable` (~65-68) keys
  the policy chain on the **producer-declared** class when present (e.g. the
  pg store's `pg/claim_unavailable`), falling back to synthetic
  `acquire/unavailable` only when the producer names nothing.
  `on_error.go::lookupPolicy` is exact-key match.

Net: on any node whose executor advertises a vocabulary (http-node,
claude-agent), a `pg/claim_unavailable:` key is rejected at registration,
while an `acquire/unavailable:` key registers but never matches the pg drain.
This repo's own scenario (`test/scenarios/pg_error_classes/…` ~141-150)
acknowledges it ("owned by the store, not the worker's executor") and routes
around via an instance-scoped `terminal/error/*` subscription.

**Ask:** either exempt producer-declared classes from the executor-vocabulary
range-check (validator learns the producers' classes the same way it learns
the executor's), or define a documented fallback-match (e.g. `acquire/*`
catches producer-declared acquisition classes too).

### 1.3 Static-validator warnings are never surfaced

The static validator emits warnings into `res.Warnings` (e.g. the
`acquire/unavailable`-advisory from `validateAcquireUnavailablePolicyAdvised`,
whose comment says "emits an advisory warning"), but neither handler projects
them: the register handler returns only `res.Errors`
(`lib/control/controlapi/templates.go` ~204-213) and `POST /templates/validate`
projects only `res.Errors` (~388-391) — `validation_warnings` in both
responses carries only validation-pipeline findings. Even
`?warnings_as_errors=true` cannot trip on a static-validator warning.

**Ask:** merge `res.Warnings` into the responses' `validation_warnings`.

### 1.4 `CommitResponse.version_id` / `producer_metadata` are declared but discarded

`claim_producer.proto` (~193-196) and the `fanout_dispatch.go` (~45-48) design
comment say `CommitResponse.version_id` is persisted to
`rimsky_claim_handles.version_id` and `producer_metadata` is surfaced in the
fan-out parent's writeback row. The runtime does neither:
`lib/runtime/peer/client.go::Commit` (~95) discards the entire response body;
the only `SetVersionID` site (`terminal_decision.go` ~293-298) sources from the
`CommitCandidate` (DataProcessing) step. A producer author following the proto
comment sets fields that silently vanish.

**Ask:** wire the response fields, or strip the persistence claims from the
proto comments until they land.

### 1.5 `validation_supported_roles` not plumbed for executor/publisher peers

`lib/control/config/publishers.go`: when a claim-producer peer advertises the
`validation` mix-in, a fresh `ClaimProducer.Capabilities` handshake learns the
live roles. Executor and publisher peers advertising `validation` are dialed,
but their supported-roles list is treated as **empty** ("their
primary-protocol caps surfaces do not yet plumb validation_supported_roles
into this function"). The wire contract implies it works for all peer kinds.

### 1.6 Smaller declared-but-inert surfaces

- `executors.<name>.tls` is parsed and carried (`resolver.go`) but enforced
  nowhere — all executor connections use insecure credentials
  (`client.go` ~43-44, "post-v1 Plan C concern"). Docs say "recorded but not
  yet enforced"; fine if intentional, but it sits in the operator-facing key
  set.
- `work_completed` is declared in the event-kind catalog
  (`lib/foundation/events/kinds.go`) but no runtime site emits it — only
  `work_started` is appended (`runner_acquire.go` ~376).
- The named-lock acquisition path (`runner_acquire_named_locks.go`) increments
  no Prometheus metric — `rimsky_claim_acquisitions_total` covers producer
  claims only, so named-lock saturation is invisible to metrics (events are
  the only observation surface).
- No subscribe-to-all lifecycle mechanism: lifecycle fan-out is scoped to
  peers referenced by a template's nodes (`lifecycle.go::peersReferencedBySpec`),
  so a purely observational subscriber must be attached as an unused store
  alias on a node of every template it should audit.

## 2. Suspected bug (code-read; no covering test)

### 2.1 Multi-`hard_dep` upstreams appear to livelock

`lib/runtime/runner_terminal.go::pullHardDepUpstreams` re-affirms (re-runs)
any hard-dep'd upstream already settled in the frame each time the receiver is
re-visited — there is no settled-this-frame guard — and the receiver's
attribute `source:` directives guarantee a re-visit at every such upstream's
terminal. With **two or more** `hard_dep: true` upstreams settling
independently in the same frame, the siblings mutually re-seed each other:
re-runs instead of a rendezvous. Single-`hard_dep` is covered
(`test/scenarios/per_run_attributes/hard_dep_test.go`); the multi case has no
test. Found by code reading during the docs reconcile — needs a reproducing
scenario test before fixing. The cookbook now warns against the shape.

## 4. Cosmetics

- One design concept file ships without the `aliases:` frontmatter key while
  the stated schema is `concept` / `status` / `aliases` (70 of 71 have it).
- Three `decision:<slug>` tokens in design concepts (`event-log.md`,
  `message.md`, `rimsky.md`) reference the design decision log, which has no
  published surface — a docs cold-reader cannot follow them.
- rimsky-docs' `marketplace.json` description says "packaged as an installable
  Claude Code skill" (singular) while the plugin ships two skills — noted here
  only because the fix was deemed churn docs-side; it is a rimsky-docs item,
  not a rimsky-core one.
