# Rimsky Intent-vs-Reality Gap Audit (Final)

## Executive summary

The user's suspicion is **partly borne out, but not in the way the complaint frames it.** The bulk of "documented but missing" surface area is concentrated in *unbuilt design sketches and deferred follow-ups* — package manager, geo type, RDK, OpenTelemetry tracing, SSE event streaming, the message-schema layer — which the codebase itself classifies as historical scratch (`.ok-planner/sketches/`), not shipped contracts. Those are honest "not built yet," not "claimed working but broken." The real reason a fresh client cannot get Rimsky working end-to-end is much narrower and more damning: **the headline onboarding path (`rimsky run <file>`) ships a correct engine with no example file to feed it, no fenced code in the README, and the only working `TemplateSpec` shapes buried in Go test structs.** A new operator literally has nothing to copy. Stacked on top of that are a cluster of "documented MUST / blessed invariant that the code doesn't enforce" defects — the mandatory `Idempotency-Key` header is silently optional, two flagship store images don't implement the fan-out RPC their own validator requires, and anonymous-mode (the documented bootstrap path) is mutually exclusive with late-bound services. So the biggest intent-vs-reality drift is at the **documentation-promise / first-run boundary**: the deeper orchestration machinery is largely real and tested, but the on-ramp and several load-bearing "guarantees" are not what the docs assert.

## Blockers

Gaps that prevent a documented core workflow from working at all. Ordered by blast radius.

### 1. `rimsky run <file>` headline dev-loop has no spec file to run
- **Claimed:** README §4 and the CLI root usage present `rimsky run <file>` as the first dev-loop verb — "Register, deploy, instantiate in one shot" from a YAML `TemplateSpec`.
- **Real:** The command and decoder are fully implemented and correct (`cmd/rimsky/cli/run.go:84-204`, `readSpecFile` at `cmd/rimsky/cli/templates.go:85-109`), **but no copyable example spec ships anywhere.** `grep -rln 'nodes:'` over non-excluded YAML returns zero hits; `README.md` has zero fenced code blocks; `examples/` holds only four gRPC protocol-service Go programs explicitly marked "not deployable services"; the only `TemplateSpec` instances in the tree are inline Go structs in test files (`test/scenarios/canary/template_registration_run_a_pass_test.go:78`, `cmd/rimsky/cli/templates_test.go`).
- **Blast radius:** This is the single most likely reason a fresh consumer cannot get Rimsky working as documented. A new user told to use `rimsky run <file>` must reverse-engineer the YAML `TemplateSpec` shape from Go source before any documented flow is reachable.
- **Source:** `README.md` §4 / `cmd/rimsky/main.go::printRootUsage` (doc-surface).

> Note: this is the one blocker whose *engine* is fine — the fix is low-effort (add one illustrative generic-named template-spec YAML under `examples/`, exercised by a test). It is listed as a blocker because it blocks the documented first-run end-to-end, which is exactly the user's complaint.

## Themes — the systemic patterns

1. **"Documented but unbuilt sketch."** The largest share of apparent gaps are forward-looking proposals under `.ok-planner/sketches/` (package manager, geo, RDK, OTel tracing, SSE streaming, message-schema, synthetic-blocker) that the repo itself classifies as historical scratch — not contracts. They read as "missing features" only if a reader treats sketches as commitments. **Mitigation:** keep sketch-sourced intent out of user-facing docs/READMEs until a spec lands; the citation grammar (`sketch:` vs `spec:`) already exists to mark this.

2. **"Documented MUST / blessed invariant the code doesn't enforce."** The `Idempotency-Key` "MUST," invariant 9b's "enforced at a code site + scenario test," the `compose:` prefix reservation, and the unified-5×-heartbeat invariant all assert guarantees the implementation does not actually hold. These are the most corrosive because operators *rely* on them. **Mitigation:** every CLAUDE.md "MUST" and every `@blessed-invariant` should have a test that fails when the guarantee is removed; several here have a test that *asserts the opposite* (e.g. `messages_test.go:267`).

3. **"Engine real, on-ramp missing."** Repeatedly the runtime is implemented and tested but the first-use affordance is absent: `rimsky run <file>` with no example file, fan-out machinery with no bundled store that advertises it, stub-mode handshake with no shared constant. The code works; a new client can't reach it. **Mitigation:** treat the documented happy-path as a tested artifact (one example spec, one fan-out-capable bundled store, one end-to-end onboarding scenario).

4. **"Happy-path only / fails silently off-path."** Anonymous-mode + late-bind, SQLite + replicas>1, callback advertise-host typos, missing idempotency key — all produce a working-*looking* stack that silently misbehaves off the happy path, with no fail-fast. **Mitigation:** add startup gates and reject-at-boundary checks for the broken-by-construction configurations the design docs already enumerate.

5. **"Doc/instruction drift inside the source."** `deploy/build-images.sh`, the `watch` "chronological" comment, the "Five source kinds" header over six bullets, the stale `schedule_fired` framing — small stale references that send a reader chasing artifacts that moved or never existed. **Mitigation:** these are cheap to fix and high-confusion; sweep them when touching the adjacent code per the "After Code Changes" rule.

**Bottom line for the user:** the suspicion that "many documented features were never built" is true for the *sketch-sourced roadmap* but mostly false for the *core orchestration engine*, which is real and tested. The actual reason no client has gotten Rimsky working end-to-end is the combination of theme 3 (no runnable onboarding example) and theme 2 (a handful of documented guarantees the server doesn't enforce). Fixing the single onboarding example, the `Idempotency-Key` guard, and at least one bundled store's `SplitScope` would move the documented core workflow from "reverse-engineer it" to "copy and run."
