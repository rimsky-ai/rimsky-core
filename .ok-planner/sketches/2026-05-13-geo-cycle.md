# Geo cycle — `geo` blessed typed-attribute

**Date:** 2026-05-13
**Status:** sketch / cycle proposal
**Dependencies:** blessed typed-attribute type-registry surface, the
Python/TypeScript executor SDKs, and the `verifier-shape-checks`
bundled executor (all from the data-platform cycle).
**Supersedes:** the `geo` section of
`.ok-planner/history/sketches/2026-05-13-blessed-typed-attributes.md`.

## What this cycle is

Adds `geo` as a blessed typed-attribute, building on the type-registry
pattern established by `blob` and `table`. `geo` is more ambitious than
`table` (CRS handling, spatial-operation surface, substrate choice
between PostGIS and GeoParquet); its own brainstorm-spec-plan-implement
loop because the design surface is rich enough to deserve focused
attention.

---

## Motivation

Geospatial data shows up in cadastral systems, transportation networks,
environmental monitoring, location analytics, geofencing, infrastructure
planning. Every workload eventually wants geometry-aware operations
(intersect, contains, within, buffer, simplify, area, length). Doing
this through claim producers means each consumer ports a different
fragment of the PostGIS / GeoPandas / Turf.js feature set.

A blessed `geo` typed attribute gives rimsky the same first-class
ergonomics for geospatial workloads that `table` gives for tabular
ones: substrate-erased above; substrate-aware under the hood; SDK
adapters that resolve to language-native spatial types.

## Type definition

- **Shape**: typed feature collection. Each feature has a geometry
  (GeoJSON-compatible types: Point, LineString, Polygon, MultiPoint,
  MultiLineString, MultiPolygon, GeometryCollection), a CRS
  declaration, and named property fields.
- **Concurrency**: RW with COW versioning, same as `table` —
  `rw_async_cow_subgraph_picks_one`. Writes never block reads;
  concurrent writers fork into versions; holding-subgraph aggregate
  outcome picks one. Same state-machine-shape footgun as `table`;
  escape hatch is claim against a substrate with proper transactional
  semantics.
- **Lifetime**: `subgraph` by default; `durable` via opt-in. Same
  machinery as `table`.
- **Backing store**: rimsky-managed. Operator picks per cluster (or per
  type if multi-backing within a type lands as a future option):
  - **PostGIS-backed** — transactional, indexed, spatial query
    support. Schema-per-attribute (or table-per-attribute within a
    shared schema). Versioning via row-timestamps or branch-style.
  - **GeoParquet-with-WKB** — Parquet files with WKB-encoded geometry
    columns and the GeoParquet metadata convention. Cheaper for batch;
    no transactional or indexed-query surface.
- **Wire**: handle reference passed via substitution; the SDK adapter
  resolves to substrate-native spatial types.
- **Schema evolution**: same stance as `table` — additive evolution
  permitted with reader tolerance for absent newer fields; non-
  additive evolution produces a new major version with no compatibility
  claim.

## SDK adapters

Python and TypeScript SDKs gain `geo` adapters. Python first, TS
fast-follow.

### Python

- `to_geopandas()` → `geopandas.GeoDataFrame`.
- `to_geoarrow()` → Arrow table with GeoArrow extension type for the
  geometry column.
- `iter_features()` → iterator of `{geometry, properties, crs}` dicts.
- `spatial_query(predicate, geometry)` → filter by spatial predicate
  (intersects | contains | within | overlaps | touches | crosses |
  equals).

Writers symmetric: `write_geopandas`, `write_geoarrow`,
`write_features`.

### TypeScript

- `toGeoArrow()` — Arrow + GeoArrow.
- `iterFeatures()` — async iterator.
- `spatialQuery(predicate, geometry)` — filter.

TS spatial ergonomics are weaker than Python's (no equivalent of
GeoPandas in the JS ecosystem); the adapter focuses on getting bytes
out and accepting Turf-shaped input.

## Spatial operations surface

A curated subset of operations is surfaced via the SDK:

- **Predicates**: `intersects`, `contains`, `within`, `overlaps`,
  `touches`, `crosses`, `equals`.
- **Measures**: `area`, `length`, `distance`, `bbox`.
- **Constructors**: `buffer`, `simplify`, `convex_hull`, `centroid`.
- **Set operations**: `union`, `intersection`, `difference`,
  `symmetric_difference`.

Substrate-aware execution pushes these to the backing store when
possible. PostGIS adapter generates `ST_Intersects`, `ST_Buffer`,
`ST_Union` server-side; GeoParquet adapter loads features client-side
and uses Shapely (Python) / a chosen JS geom library (TypeScript) for
the operation.

Pushdown vs client-side is invisible to the consumer; the SDK picks
based on the operator-configured substrate. Documentation surfaces the
performance implications.

## CRS handling

Geospatial workloads frequently span CRSes (e.g. ingest in source CRS,
reproject to a working CRS, output in a delivery CRS). The blessed
type handles this honestly:

- Each `geo` attribute declares its CRS at the template level.
- The substrate stores features in the declared CRS.
- Cross-CRS operations (e.g. spatial query of features in EPSG:4326
  against a polygon in EPSG:3857) are detected by the SDK; the SDK
  reprojects on the smaller side (typically the query geometry) and
  performs the operation.
- Reprojection at write-back is an explicit consumer action:
  `outputs.parcels.write_geopandas(df.to_crs("EPSG:4326"))` — the SDK
  doesn't silently reproject on the consumer's behalf, because the
  consumer might want to error rather than reproject.

## Worked example

`docs/agents/examples/geo-pipeline.md` — a load-transform-verify-publish
geo pipeline:

1. `load-parcels` — `http-node` fetches parcels from a GIS endpoint;
   writes a `geo` attribute in source CRS.
2. `reproject-parcels` — Python executor reads `parcels` via
   `to_geopandas`, reprojects, writes `parcels_3857`.
3. `validate-parcels` — `verifier-shape-checks` (with `geo`-aware
   checks: `geometry_valid`, `geometry_type_in_set`,
   `crs_matches_declaration`).
4. `compute-overlaps` — Python executor performs spatial join against
   a separate `zoning_districts` `geo` attribute; writes
   `parcel_zoning_overlap` `table` attribute (joining `geo` and
   `table` outputs).
5. `publish-overlap` — durable-lifetime `table` attribute persisted
   beyond the run.

Demonstrates: substrate-erased reading via `to_geopandas`; cross-CRS
operations; spatial joins; mixing `geo` and `table` outputs;
`verifier-shape-checks` with geo-shaped checks.

## Implementation surface

- **`foundation/typed_attributes/geo/`** — type driver with two
  backing-store implementations (PostGIS and GeoParquet).
- **`rimsky.yml` extension**:

  ```yaml
  typed_attributes:
    geo:
      backing: postgis
      postgis:
        dsn: postgres://...
        schema: rimsky_geo
        versioning: branch          # or row_timestamp
  ```

  or

  ```yaml
  typed_attributes:
    geo:
      backing: geoparquet
      geoparquet:
        bucket: rimsky-geo
        prefix: prod/
        versioning: prefix
  ```

- **Python SDK adapter** — `@rimsky/sdk-python` extension; depends on
  `geopandas`, `shapely`, `pyarrow`, `geoarrow`.
- **TypeScript SDK adapter** — `@rimsky/sdk-typescript` extension;
  depends on Arrow JS + a chosen geom library.
- **`verifier-shape-checks` extension** — add geo-aware checks:
  `geometry_valid`, `geometry_type_in_set`, `crs_matches_declaration`,
  `feature_count_ratio`, `bbox_within_bounds`. Re-use existing builtin
  shape-check infrastructure.
- **`rimsky-cli` introspection** — `geo` attribute state includes CRS,
  feature count, bbox, substrate.

## Open design questions

1. **Substrate flexibility within `geo`.** Should the operator be able
   to mix backings (some `geo` attributes on PostGIS, others on
   GeoParquet, based on size/predicate-pushdown needs)? Probably yes
   eventually, but start with one backing per cluster (same stance as
   `table`).
2. **GeoArrow maturity.** GeoArrow as a transport format is still
   maturing in 2026. The SDK should support both raw WKB-in-Arrow and
   GeoArrow extension types; consumers pick. As GeoArrow stabilizes,
   it becomes the default.
3. **CRS as part of the type identity.** Does
   `attributes.parcels: { type: geo, crs: "EPSG:4326" }` make CRS part
   of the attribute's identity (and a reprojection produces a new
   attribute), or is CRS metadata on the value that can change between
   writes? Lean: CRS is part of the schema; non-additive change to CRS
   produces a new major version (matches `table` schema-evolution
   stance).
4. **Spatial-index management.** PostGIS substrate needs GIST indexes
   on geometry columns. Auto-created at attribute-registration time?
   Or operator-managed? Lean auto-managed for ergonomics.
5. **GeoParquet versioning strategy.** Prefix-per-version is the
   simplest; manifest-pointer is the more sophisticated. Sequence:
   prefix-per-version first; revisit if version count grows large.
6. **Predicate pushdown taxonomy.** Which spatial operations are
   guaranteed to push down to PostGIS? Document the matrix; client-
   side fallback is the safety net.
7. **Concurrency: shared spatial index under multi-writer.** PostGIS
   index updates are serialized per-table; concurrent writers may
   experience contention. The COW-versioning model side-steps this
   (each writer's staging area is its own table or branch), but
   confirm during implementation.

## Phasing within the cycle

1. **`geo` type-driver foundation.** Both PostGIS and GeoParquet
   backings. CRS storage and metadata.
2. **Python SDK `geo` adapter.** `to_geopandas`, `to_geoarrow`,
   `iter_features`, `spatial_query`. Symmetric writers.
3. **`verifier-shape-checks` geo extensions.** New check types added
   to the bundled executor.
4. **Worked example.** `docs/agents/examples/geo-pipeline.md`.
5. **TypeScript SDK `geo` adapter.** Same surface, TS-idiomatic.

Steps 1–4 are sequenced. Step 5 can run in parallel with 4 if labor
allows.

## What this isn't

- **Not a full GIS platform.** The spatial-operations surface is
  curated, not comprehensive. Consumers needing operations the SDK
  doesn't expose (e.g. ST_3DIntersects, exotic projection-specific
  operations) drop down to the substrate-native client.
- **Not a CRS-translation framework.** Reprojection is the consumer's
  explicit action; the SDK doesn't silently reproject.
- **Not a streaming-geo type.** Append-only geospatial event streams
  (e.g. real-time vehicle telemetry) are a different shape and not in
  scope for `geo`. They'd be a future `geo_stream` or a `stream` with
  spatial-aware payload.
