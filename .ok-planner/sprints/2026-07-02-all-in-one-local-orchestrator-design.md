# All-in-one local orchestrator

The all-in-one deployment today runs the three rimsky roles (scheduler, supervisor, control-api) in one process but still talks to bundled services as external gRPC endpoints, so "local orchestrator" currently means "plus a docker-compose stack." This spec closes that gap for the two service categories that fit the in-proc handler pattern (executors, claim producers): bundled handlers register in-process in the all-in-one process (dual-mode alongside their existing standalone gRPC deployments); the claude-agent executor is ported from TypeScript to Go so it can run in-process without a Node runtime; `rimsky run <template>` self-hosts a full stack by default; and two claude-agent knobs previously configured on the executor container (its MCP catalog and its expose-env allowlist) surface as per-node template configuration. The per-node MCP declarations extend the inline schema to cover the three semantically distinct transports the current implementation supports (http, stdio, module — where "http-loopback" is a runtime alias for module); the inline schema is HTTP-only today, so this is an extension, not just a preservation. Sensors and lifecycle-subscribers are out of scope — their protocol shapes (outbound-emitter and event-callback) don't fit the executor-shaped in-proc pattern and their real bundled implementations either don't exist or don't match the shape. Rimsky.yml is unchanged; bundled handlers in all-in-one read the same env vars they'd read on their standalone service containers.

Two design artifacts are intentionally NOT mutated by this spec and require no action from the plan phase: `concept:executor` already recognizes both in-process handlers and out-of-process services under an identical protocol surface (both forms are named in its current body); and `story:inproc-utility-executor` describes the built-in utility kinds (loop_counter, attribute_passthrough, emit_message) whose scope is unaffected by the bundled-services in-proc extension — bundled services and utility executors reuse the same in-proc registry mechanism but remain distinct concepts.

## User outcomes

**STORY-local-orchestrator-zero-config** — As a local user (a developer iterating on templates against files on my own machine), I can run an ad-hoc template through the rimsky all-in-one process with no rimsky.yml and no external service infrastructure for the bundled executors and claim producers the template references, so that I iterate locally without a docker/compose stack — driving real bundled services (real claude CLI spawn, real filesystem reads) end-to-end.
**Acceptance:** I run the all-in-one process against a local template file. The template's references — a filesystem claim producer, a claude-agent executor — resolve to bundled handlers running in the same process. The graph drives to terminal doing real work (real claude subprocess, real filesystem side effects). I observe the terminal attribute state and the side effects on my local disk. No config file was authored, no docker daemon was involved, no external processes were stood up for the bundled kinds the template referenced.
**Falsifier:** I have to author a rimsky.yml or other config file before an ad-hoc run works; OR I have to run `docker compose up` or stand up separate service processes for the bundled executors or bundled claim producers to work; OR a bundled-service dispatch hits a stub or canned reply instead of doing the real work (the claude-agent handler doesn't spawn claude, the filesystem producer doesn't read disk).
**Proof:** Executable proof — an integration test drives an ad-hoc template through the all-in-one CLI with no rimsky.yml and no external processes running. The template references a filesystem claim producer and a claude-agent executor. The test asserts terminal graph state, real filesystem side effects, and real claude subprocess execution.

**STORY-portable-template-across-modes** — As a rimsky user (a developer promoting a locally-authored template to production, or an operator adopting a template someone else authored), I can use the same template file in both modes — all-in-one and multi-container — without editing it, so that there's no dev-vs-prod template dialect and locally-working templates are directly promotable.
**Acceptance:** A template that dispatches to bundled executors and claim producers runs to the same terminal graph shape under all-in-one (in-process handlers) and under a containerized deployment (standalone gRPC bundled-service images), with no changes to the template file, GIVEN a normalized operator context across the two runs (same env-var values readable by the bundled handlers, same clock domain, same input files). What differs between modes is what belongs to modes — the rimsky.yml naming external service endpoints (containerized) or its absence (all-in-one), and per-service env vars set on the appropriate process (all-in-one process env vs container env). The template's node config, its structure, and its referenced service kinds are byte-identical across modes.
**Falsifier:** The template needs edits (any change to node config, template structure, referenced service kind names, or per-node service declarations) to run in the other mode; OR the same template file byte-for-byte reaches a different terminal graph shape under the two modes when the operator context is normalized (differences in blob-handle payloads and other persistence-backend-inherent opaque values are permitted; the graph's terminal shape and each node's terminal tag class must agree).
**Proof:** Executable proof — a scenario test drives the same template file byte-for-byte through both modes: once through the all-in-one process (in-process handlers, no rimsky.yml) and once through a containerized deployment (standalone bundled-service images named in a rimsky.yml). The two runs share a normalized operator context. The test asserts template-byte-equality between the two runs, then asserts terminal-graph-shape equality (same nodes reach terminal, same terminal tag class per node), tolerating persistence-backend-inherent differences in opaque handle values.

**STORY-claude-agent-mcp-servers-per-node** — As a template author using the bundled claude-agent executor, I declare on each node the list of MCP servers that node's dispatch may reach (each server's transport type — http, stdio, or module — and its transport-appropriate parameters) inline in the node config, while the operator running the claude-agent service separately declares an allowlist restricting which MCP server references any template may use; the service enforces the intersection. So that template authors own per-node MCP surfaces and operators own the boundary of what's permitted, without either reaching across into the other's territory.
**Acceptance:** I author a template with two claude-agent nodes, each declaring a different MCP server list in its node config, drawing from any of the three supported transports. The operator's allowlist covers both nodes' declared servers. Each node dispatches; each real handler's MCP surface at spawn matches its own node's declaration observably — the CLI child's MCP config reflects that node's servers, and the child's MCP calls reach exactly the servers that node declared and no others. No operator-side rimsky.yml block keyed by node name is needed to make each node's declaration effective. Separately, when the operator's allowlist excludes a server that a node declares, the service rejects that dispatch with an operator-facing error naming the disallowed server, the template, and the node.
**Falsifier:** Two claude-agent nodes with different declared MCP server lists observably reach the same MCP surface at spawn; OR a node declaring an MCP server outside the operator's allowlist dispatches anyway and reaches the disallowed server; OR the inline schema retains only a subset of the three transports (any of http / stdio / module becomes unreachable via per-node declaration); OR the per-node MCP list requires operator-side keying (rimsky.yml, service container env keyed by node); OR the rejection error is generic (doesn't name the disallowed server, template, or node); OR rimsky's own dispatch payload or protocol shape gains an MCP-related field (the redesign must live inside the claude-agent service, not in rimsky's dispatch path).
**Proof:** Executable proof — a scenario test registers a template with claude-agent nodes declaring different MCP server sets in their node configs, with declarations together covering all three supported transports (http, stdio, module); the operator config allowlists cover the declared servers. The test dispatches the nodes and asserts observable per-node MCP behavior — each spawned CLI child reaches exactly the servers its own node declared and no others. A second scenario adds a node declaring an off-allowlist MCP server; the test asserts the service rejects that dispatch with an error naming the disallowed server, template, and node. An additional assertion greps rimsky's protocol surface for MCP-related fields and confirms none were added by this spec.

**STORY-claude-agent-expose-env-per-node** — As a template author using the bundled claude-agent executor, I declare on each node the list of env-var names that should be exposed to that node's CLI child (so the agent can read them from its own environment) inline in the node config, while the operator running the claude-agent service separately declares an allowlist restricting which env-var names any template may expose; the service enforces the intersection. So that template authors own per-node secret needs and operators own the boundary of exposable env, without either reaching across into the other's territory and without secrets ever landing in rimsky's persisted attribute bag.
**Acceptance:** I author a template with two claude-agent nodes, each declaring a different expose-env list in its node config (node A wants `VALIDATOR_TOKEN` exposed; node B wants some other env-var name exposed). The operator's allowlist covers both names. Each node dispatches; each spawned CLI child sees only the env vars its own node declared present in `process.env` (VALIDATOR_TOKEN visible to A's child but not B's; the converse for B). No plaintext env value appears in rimsky's persisted attribute bag. No operator-side rimsky.yml block keyed by node name is needed. Separately, when the operator's allowlist excludes an env-var name that a node declares, the service rejects that dispatch with an operator-facing error naming the disallowed env-var name, the template, and the node.
**Falsifier:** Two claude-agent nodes with different declared expose-env lists observably see the same env-var set in their CLI children's `process.env`; OR a node declaring an env-var name outside the operator's allowlist dispatches anyway and gets that env var passed through; OR the per-node expose-env list requires operator-side keying (rimsky.yml, service container env keyed by node); OR the rejection error is generic (doesn't name disallowed env-var, template, or node); OR a plaintext env-var value appears in rimsky's persisted attribute bag; OR rimsky's own dispatch payload or protocol shape gains an expose-env field (the redesign must live inside the claude-agent service).
**Proof:** Executable proof — a scenario test registers a template with two claude-agent nodes declaring different expose-env sets; the operator's allowlist covers both names. The test dispatches both nodes and asserts observable per-node env visibility — each spawned CLI child sees exactly the env vars its own node declared (via witness — the child writes the env vars it saw to a per-node file, or the child's MCP calls carry the values back). An additional assertion greps rimsky's persisted attribute bag for the plaintext values and confirms neither appears. A second scenario adds a third node declaring an off-allowlist env-var name; the test asserts the service rejects that dispatch with an error naming the disallowed env-var, template, and node. An additional assertion greps rimsky's protocol surface for expose-env-related fields and confirms none were added.

## Technical decisions

**TD-handler-package-in-service-directory** — Bundled service handler code lives in one or more handler packages inside each bundled-service directory under `code:lib/services/`; both the standalone gRPC `main` and the all-in-one entrypoint consume the same handler code.
**Choice:** Each in-scope bundled service directory exposes its handler code as importable Go packages under the service directory. The standalone binary constructs a handler and serves it over gRPC (unchanged operational shape). The all-in-one entrypoint constructs the same handler and registers it into the in-proc dispatch pool. Physical layout may vary per service — executors (`code:lib/services/executors/claude-agent/`, `code:lib/services/executors/http-node/`) today have a flat `main.go` plus handler code in the same package; claim producers (`code:lib/services/claim_producers/filesystem/`, `code:lib/services/claim_producers/postgres/`) today have `cmd/main.go` plus handler code split across `server/`, `store/`, `lifecycle/` subpackages. The spec preserves each service's existing layout; the invariant is that a handler package (or set of packages) is importable and reusable across both surfaces.
**Rationale:** The services module already imports only the protocols module; existing handler code inherits that isolation. Layouts differ because services have different internal shapes; forcing a uniform layout adds no value.
**Alternatives:** (i) Mandate a uniform `handler/` subpackage per service — rejected: forces restructuring of claim-producer directories that already have coherent subpackage splits. (ii) Extract handler code into a new Go module `lib/service-handlers/` — rejected: pays new-module tax for marginally stricter isolation.

**TD-per-service-load-opts-from-env** — Each bundled service's handler package exposes a `LoadOptsFromEnv()` function that both the standalone `main` and the all-in-one entrypoint call.
**Choice:** Each handler package defines `LoadOptsFromEnv() (Opts, error)` reading its operator env vars into a per-service opts struct. The standalone `main.go` calls it to construct the gRPC-hosted handler; `bundled.RegisterAll` calls the same function per service to construct the in-proc handler. Neither surface re-parses the same env vars twice.
**Rationale:** Single source of truth for each service's operator env-parsing; the same env produces the same handler behavior across modes without duplicated parsing code.
**Alternatives:** Have `bundled.RegisterAll` accept pre-constructed opts from callers — rejected: pushes env-parsing responsibility onto every all-in-one entrypoint invocation and defeats the "same behavior across modes" property.

**TD-parallel-inproc-claim-producer-registry** — The runtime layer gains an in-proc registry for the claim-producer protocol covering the full protocol surface.
**Choice:** Add `lib/runtime/claimproducer/InProcessRegistry` shaped like the existing `code:lib/runtime/executor/InProcessRegistry` (bind name → handler; in-proc client bypasses gRPC). The registry supports the four core claim-producer verbs (Open, Commit, Abandon, Release) plus the optional mix-ins (split-scope, scopes-conflict, validation, data-processing) — handlers advertise which mix-ins they implement at registration time, and the in-proc dispatch path routes by (name, verb) matching the gRPC path shape. Capability advertisement into `concept:discovery-cache` is served by the registration entrypoint (each handler declares its capabilities as construction data; the entrypoint populates the cache).
**Rationale:** Executors already have an in-proc registry with a single-verb Execute surface; claim producers need the parallel piece but must express the fuller multi-verb + mix-in shape to match the gRPC contract semantically.
**Alternatives:** (i) Loopback gRPC via `bufconn` or Unix socket — rejected: introduces the exact wire-serialization overhead in-proc is meant to eliminate. (ii) Core-verbs-only registry (drop mix-ins) — rejected: creates a capability asymmetry between modes, violating STORY-portable-template-across-modes.

**TD-bundled-executor-inproc-capability-advertisement** — Bundled executor handlers advertise their schema / declared tags / declared error classes into `concept:discovery-cache` at registration time, bypassing the gRPC observability handshake.
**Choice:** Each bundled executor handler package exports `SchemaBytes()`, `DeclaredTags()`, and `DeclaredErrorClasses()` at package scope. `bundled.RegisterAll` populates the discovery cache with each handler's schema (parallel to utility executors' `builtin.SchemaFor` at `code:lib/runtime/executor/builtin/builtins.go`), tags (parallel to `builtin.DeclaredTagsFor`), and declared error classes (new — utility executors currently declare no error classes so no analogous `builtin.*` accessor exists; bundled executors add this dimension to the cache). Standalone gRPC deployment path uses the observability handshake as today; in-proc path uses this registration-time population.
**Rationale:** In-proc handlers do not receive gRPC handshakes; without an explicit advertisement path, the discovery cache is empty and STORY-claude-agent-mcp-servers-per-node's per-node schema validation cannot dispatch.
**Alternatives:** Run a loopback gRPC handshake for each in-proc handler — rejected: reintroduces the overhead in-proc is meant to eliminate.

**TD-bundled-registry-entrypoint** — A single package registers all bundled service handlers across the two in-proc registries.
**Choice:** New package `lib/services/bundled/` exports `RegisterAll(execReg, cpReg, aliases, discovery, opts)`. The all-in-one entrypoint calls `builtin.RegisterAll` (utility executors, unchanged) then `bundled.RegisterAll` (new). The entrypoint imports each bundled service's handler package directly; failures to construct any single handler abort the all-in-one boot with a clear error naming which handler failed.
**Rationale:** Atomic registration point; each bundled service contributes to it via its handler package.
**Alternatives:** Per-service init() side effects — rejected: convention-based registration violates Plumbline (explicit registration only).

**TD-rimsky-run-self-hosts-templates** — The `rimsky run <template>` verb self-hosts an all-in-one stack when no target endpoint is present.
**Choice:** `rimsky run <template>` boots an in-process all-in-one stack (reusing the machinery `code:cmd/rimsky/cli/compose/run.go` already uses), registers bundled handlers via `bundled.RegisterAll`, registers + deploys + instantiates the template against the local control-api, streams events to stdout, and exits when the instance reaches terminal. Passing `--endpoint <url>` (or having one configured via `rimsky ctx`) suppresses self-hosting and reverts to the existing dev-loop dispatch against a remote rimsky. A user with a configured `rimsky ctx` endpoint who wants explicit self-host may pass `--self-host` to override (bypasses the context endpoint).
**Rationale:** Presence of a target endpoint is a natural discriminator for the common case; `--self-host` gives the explicit escape hatch for users with stale context configs.
**Alternatives:** New top-level verb — rejected: bloats CLI surface for no ergonomic gain.

**TD-rimsky-compose-run-scope** — `rimsky compose run <manifest>` remains the self-host + one-shot for compose manifests.
**Choice:** `rimsky compose run <manifest>` keeps its current shape. Not extended to accept templates; `rimsky run <template>` covers that case. `rimsky compose up | down | plan | status` unchanged.
**Rationale:** Verb-to-input 1:1 with no autodetect ambiguity.
**Alternatives:** Extend `compose run` via autodetect — rejected: makes verb behavior depend on file-content inspection; ambiguous error messages.

**TD-late-bound-services-direct-spawn** — Late-bound `--service` bindings under self-hosted `rimsky run` use the `hostagent.SpawnService` primitive directly, matching the compose-run pattern.
**Choice:** Under `rimsky run <template> --service <name>=<path>` in self-host mode, the CLI reuses the direct-spawn code path `code:cmd/rimsky/cli/compose/run.go::spawnServices` uses — calling `hostagent.SpawnService` per late-bound binding to spawn each on a loopback gRPC port, then synthesizing an ephemeral `ManifestExecutorEntry{Transport: "grpc", Endpoint: "127.0.0.1:<port>"}` into a synthetic rimsky.yml (per compose-run's existing `WriteSyntheticRimskyYAML`) so the self-hosted stack dials the loopback endpoints as ordinary registered executors. Late-bound services are therefore out-of-process, loopback-reached (matching compose-run semantically), NOT in-proc handlers — the in-proc path is reserved for bundled services. No separate `rimsky-host-agent` daemon is auto-started; no host-agent-proxy config is required.
**Rationale:** The `hostagent` package already exposes the spawn primitive as a callable unit; compose-run already uses it directly without the daemon. Reusing that path under self-hosted `rimsky run` gives one code path for both compose and template self-host cases with no proxy plumbing.
**Alternatives:** (i) Auto-start the `rimsky-host-agent` daemon and synthesize a proxy entry in ephemeral rimsky.yml — rejected: extra processes, extra config synthesis, duplicates compose-run's simpler shape. (ii) Error on `--service` under self-host — rejected: loses functionality.

**TD-cli-spawn-mechanism** — The claude-agent Go handler spawns the `claude` binary as a subprocess.
**Choice:** Handler shells to the `claude` binary via the Go standard subprocess mechanism, with argument and env composition mirroring the retired TypeScript implementation's behavior.
**Rationale:** The retired TypeScript version is itself a subprocess spawner (`code:lib/services/executors/claude-agent/src/cli-runner.ts` uses `node:child_process.spawn`); the Go port replaces the Node runtime with the standard-library primitive and drops one process layer.
**Alternatives:** Reimplement Claude's session protocol against the raw HTTP API — rejected: reinvents wheels the CLI already handles and diverges from the CLI's evolving surface.

**TD-internal-mcp-server-net-http** — The claude-agent handler's internal MCP server uses the standard-library HTTP stack.
**Choice:** The per-handler-instance MCP endpoint is a standard-library HTTP server speaking the JSON-RPC subset the CLI child uses today.
**Rationale:** Standard library only; JSON-RPC subset is small enough that a third-party MCP library would add dependency surface without ergonomic gain.
**Alternatives:** Adopt a third-party Go MCP library — rejected: adds a dependency for a small verb surface.

**TD-signoff-crypto-ed25519** — Sign-off validation uses the standard-library ed25519 primitive.
**Choice:** Handler validates each declared signoff by verifying the ed25519 signature over the domain-separated accumulated bound output. Signing shape (algorithm, domain, canonicalization) unchanged from the TypeScript implementation to preserve wire compat with existing signed outputs.
**Rationale:** Standard library primitive matches the TypeScript implementation's semantics; wire-compat with existing signed outputs.
**Alternatives:** Switch to a different signature algorithm — rejected: breaks wire compat pre-v1 for no gain.

**TD-claude-agent-cli-mcp-servers-inline-only** — The `cli.mcp_servers` schema drops the operator-catalog `{ref}` shape; inline entries cover the three semantically distinct transports the current implementation supports; the retired catalog + inline-allow env vars are deleted.
**Choice:** Delete the `{ref: "<name>"}` alternative from `cli.mcp_servers`. The remaining `anyOf` variants declare inline server config per transport with a required `transport` discriminator: `{transport: "http", name, url, headers, allowed_tools}`, `{transport: "stdio", name, command, args, env, allowed_tools}`, `{transport: "module", name, module, allowed_tools}` — where `module` accepts an alias `http-loopback` (both resolve to the same module-loopback runtime path, matching the current `code:lib/services/executors/claude-agent/src/mcp-catalog.ts` union). Handler validates transport-appropriate fields per entry. Retire `env:RIMSKY_EXECUTOR_MCP_CATALOG` and `env:RIMSKY_EXECUTOR_MCP_ALLOW_INLINE` — with no catalog and inline-only entries, both are meaningless.
**Rationale:** The current inline schema is HTTP-only; the catalog reachable via `{ref}` was the only way to declare stdio or module transports. Extending inline to cover all three transports (with the module/http-loopback runtime alias preserved) closes that surface asymmetry.
**Alternatives:** Keep both shapes with an operator catalog — rejected: pre-v1 break-freely; one idiom per job.

**TD-claude-agent-cli-expose-env-field** — A new per-node `cli.expose_env` field lists env-var names to pass through.
**Choice:** Add `cli.expose_env: ["VAR_NAME", ...]` to the claude-agent node-config schema. The handler intersects each node's declared list with the operator allowlist and injects allowed names' values from the claude-agent process's env into the spawned child's env. The executor-container env var `env:RIMSKY_CLAUDE_AGENT_EXPOSE_ENV` is retired.
**Rationale:** Moves the per-node concern (what secrets this node needs) into the node config, where it belongs; keeps the operator concern (what's permitted at all) separate.
**Alternatives:** (i) Keep the operator-only allowlist without a per-node knob (status-quo shape) — rejected: forces every operator-permitted env var into every dispatched CLI child, giving nodes no way to scope what they actually need. (ii) Per-node declaration without an operator allowlist safeguard — rejected: template authors would gain unilateral control over which secrets the CLI child sees; per `decision:claude-agent-env-passthrough-allowlist` the prior "which secrets are visible at all" decision belongs to the operator. The intersection preserves that operator control while letting template authors scope their per-node needs.

**TD-node-config-schema-format-go** — The claude-agent Go handler carries the node-config schema as an embedded JSON Schema string, validated at dispatch via the same JSON-Schema library rimsky already uses.
**Choice:** The Go handler package embeds the JSON Schema for `cli.*` node config as a string constant (or an embedded file via `//go:embed`) and validates each dispatch's node config against it with `github.com/santhosh-tekuri/jsonschema/v5` — the same library rimsky uses at `code:lib/graph/attribute/validate.go:13` and `code:lib/graph/node/template_validator.go:16`. Format and content parity with the current `code:lib/services/executors/claude-agent/src/expected-attributes-schema.ts` output.
**Rationale:** Preserves the schema as a portable artifact (identical bytes across TypeScript and Go); matches the JSON-Schema library rimsky already ships, so no new dependency surface is added.
**Alternatives:** (i) Re-express the schema as Go structs with tag-driven validation — rejected: divergent representations across the retired TS and new Go paths risk drift; the JSON-Schema embed keeps parity. (ii) Adopt a different Go JSON-Schema library — rejected: matching rimsky's existing choice avoids duplicating a dependency for the same job.

**TD-policies-service-side-enforcement** — Policy enforcement lives entirely inside each bundled service.
**Choice:** The claude-agent handler enforces its own operator allowlists (MCP server references, exposable env-var names) inside its handler code. When enforcement rejects a dispatch, the service returns an executor-protocol error outcome naming the specific violation. Rimsky does not read, validate, or acknowledge policy content.
**Rationale:** Rimsky remains inert to service-specific policy shape.
**Alternatives:** Rimsky-side pre-filter at registration or dispatch — rejected: couples orchestration to service-specific concerns.

**TD-allowlist-defaults-open** — Bundled service allowlists default to open when the operator config is absent.
**Choice:** If the operator env vars carrying the claude-agent allowlists are unset, the handler constructs with all policy allowlists open — every reference the template makes is accepted.
**Rationale:** Zero-config local dev works out of the box; operators wanting policy set env explicitly.
**Alternatives:** Default closed — rejected: breaks the zero-config local-orchestrator story.

**TD-env-var-convention-across-modes** — Bundled handlers read the same operator env vars in both modes.
**Choice:** Each bundled service handler reads its own operator config from the process's env — same env-var names in containerized mode (set on the service container) and all-in-one mode (set on the all-in-one process). Rimsky.yml carries no per-service config content in either mode. `rimsky run`'s ephemeral-run env plumbing (per `code:cmd/rimsky/cli/compose/run.go::snapshotAndSetEnv`) MUST NOT clear or reset operator env vars destined for bundled handlers — those pass through the ephemeral wrapper unchanged.
**Rationale:** One convention across modes; zero rimsky.yml schema change.
**Alternatives:** Add an opaque `config:` path field per rimsky.yml entry — rejected: introduces a schema field for a case env vars already handle.

**TD-operator-env-namespaced-per-service** — Operator env vars introduced by this spec use the `RIMSKY_<SERVICE>_*` prefix.
**Choice:** New operator env vars introduced by the claude-agent handler use the `RIMSKY_CLAUDE_AGENT_*` prefix — specifically `RIMSKY_CLAUDE_AGENT_MCP_ALLOWLIST` (replaces the retired `RIMSKY_EXECUTOR_MCP_CATALOG` and `RIMSKY_EXECUTOR_MCP_ALLOW_INLINE`) and `RIMSKY_CLAUDE_AGENT_EXPOSE_ENV_ALLOWLIST` (renames + reshapes the retired `RIMSKY_CLAUDE_AGENT_EXPOSE_ENV`). Analogous namespacing applies to any other bundled service that adds operator env vars. Existing generic per-executor env vars (`RIMSKY_EXECUTOR_PORT_HTTP`, `RIMSKY_EXECUTOR_PORT_GRPC`, `RIMSKY_EXECUTOR_HOST`, `RIMSKY_EXECUTOR_CLAUDE_BINARY`, etc.) survive unchanged — these are relevant only to standalone gRPC deployment; the in-proc path binds no ports and reads no gRPC-transport envs, so cross-service collision is not a real hazard.
**Rationale:** In all-in-one the claude-agent handler shares its process env with rimsky-core env vars (e.g. `env:RIMSKY_PROCESS_ROLE`). Namespacing prevents collision on the new operator envs; the surviving generic per-executor envs are transport-only and don't fire in-proc, so collisions don't materialize.
**Alternatives:** Non-namespaced `MCP_ALLOWLIST` / `EXPOSE_ENV_ALLOWLIST` — rejected: risks collision with unrelated env in the host process; makes provenance unclear.

**TD-http-bridge-preserved** — The Go claude-agent preserves the current HTTP-JSON bridge surface.
**Choice:** The Go port includes an HTTP-JSON bridge equivalent to `code:lib/services/executors/claude-agent/src/http-bridge.ts` on the same port env var (`env:RIMSKY_EXECUTOR_PORT_HTTP`). Callers dispatching via HTTP-JSON instead of gRPC continue to work. The HTTP bridge fires only in standalone-gRPC deployments (in-proc bypasses both surfaces).
**Rationale:** External callers depending on the HTTP surface should not have to change protocols for the Go port.
**Alternatives:** Drop the HTTP bridge — rejected: breaking change without benefit.

**TD-process-role-unified-message-covers-rimsky-run** — The `RIMSKY_PROCESS_ROLE=unified` marker's help text is updated to name all three paths that set it.
**Choice:** The blob-config error at `code:lib/foundation/persistence/blob_config.go` (currently naming only "rimsky-entrypoint's no-command all-in-one path") is updated to name the three paths that legitimately set `RIMSKY_PROCESS_ROLE=unified`: rimsky-entrypoint's no-command path, `rimsky compose run`, and `rimsky run <template>` in self-host mode.
**Rationale:** The `RIMSKY_PROCESS_ROLE=unified` gate is invariant-load-bearing (per `concept:blob-backend`) and its documentation must name all setters or drift will confuse operators reading the error.

**TD-typescript-claude-agent-retirement** — The TypeScript claude-agent implementation is deleted atomically with the Go port; the fake-cli test scaffolding is structurally rewritten.
**Choice:** Delete the TypeScript source, npm build machinery, dist output, and its Dockerfile. Replace the Dockerfile with a Go one shaped like `code:lib/services/executors/http-node/Dockerfile.http-node` (distroless base). ## Design

### Handler package layout

Each in-scope bundled service directory under `code:lib/services/` exposes its handler code as importable Go packages. Physical layout differs per service — executors have a flat `main.go` plus handler code in the same package; claim producers have `cmd/main.go` plus handler code across `server/`, `store/`, `lifecycle/` subpackages. Both layouts are preserved. The invariant is that a handler package (or coherent set of packages) is reachable by name and constructible via a per-service `LoadOptsFromEnv()` function (TD-per-service-load-opts-from-env), and both the standalone binary and the all-in-one entrypoint consume the same code.

### Bundled registration flow

The existing utility-node executor registration at `code:lib/runtime/executor/builtin/builtins.go::RegisterAll` binds `KindName → ExecutorAlias → InProcURL → handler`, dispatched via `code:lib/runtime/executor/inproc_client.go` (direct function call rather than gRPC). Bundled executor handlers (claude-agent, http-node, verifier-http, verifier-shape-checks) reuse the executor in-proc registry directly, each exposing `SchemaBytes()`, `DeclaredTags()`, and `DeclaredErrorClasses()` at package scope (TD-bundled-executor-inproc-capability-advertisement).

Claim producers currently have no in-proc dispatch path. TD-parallel-inproc-claim-producer-registry adds an in-proc registry for the claim-producer protocol under `lib/runtime/claimproducer/`, covering the four core verbs (Open, Commit, Abandon, Release), the optional mix-ins (split-scope, scopes-conflict, validation, data-processing), and capability advertisement into `concept:discovery-cache`. TD-bundled-registry-entrypoint adds `lib/services/bundled/RegisterAll(execReg, cpReg, aliases, discovery, opts)` — a single call the all-in-one entrypoint uses to register every bundled handler; each handler's opts are constructed by the handler package's own `LoadOptsFromEnv()` (TD-per-service-load-opts-from-env), so no env-parsing code is duplicated between the standalone `main.go` and the all-in-one entrypoint.

### CLI ad-hoc run entrypoint

TD-rimsky-run-self-hosts-templates extends `rimsky run` to self-host by default. When invoked without an endpoint (no `--endpoint`, no `rimsky ctx` current endpoint) — or when `--self-host` is passed explicitly to override a context endpoint — the verb reuses the compose-run self-host machinery at `code:cmd/rimsky/cli/compose/run.go`: boots the role stack in-process, waits for control-api ready, applies the local plan (register + deploy + instantiate for one template), watches events until instance terminal, exits. Bundled handlers are registered before control-api ready via `bundled.RegisterAll`. With `--endpoint` (or a `rimsky ctx` current endpoint and no `--self-host` override), `rimsky run` dispatches remotely as today.

Late-bound services (`--service <name>=<path>`) under self-hosted `rimsky run` reuse the direct-spawn code path from `code:cmd/rimsky/cli/compose/run.go::spawnServices` — calling `hostagent.SpawnService` per binding (TD-late-bound-services-direct-spawn). No separate `rimsky-host-agent` daemon is auto-started; no host-agent-proxy config is required.

`rimsky compose run <manifest>` continues to handle self-host + one-shot for compose manifests; `rimsky compose up | down | plan | status` are unaffected. The ephemeral-run env plumbing (`code:cmd/rimsky/cli/compose/run.go::snapshotAndSetEnv`) must preserve operator env vars destined for bundled handlers (`RIMSKY_CLAUDE_AGENT_*` etc.) — passing them through unchanged (TD-env-var-convention-across-modes).

### Claude-agent Go port

The port replaces the TypeScript implementation with a Go handler package + gRPC main + HTTP-JSON bridge (per TD-http-bridge-preserved). The handler shells to the `claude` binary via the standard subprocess mechanism (TD-cli-spawn-mechanism), hosts an internal MCP endpoint via the standard-library HTTP stack (TD-internal-mcp-server-net-http), validates sign-offs via the standard-library ed25519 primitive (TD-signoff-crypto-ed25519), advertises node-config schema + declared tags + declared error classes via package-scope functions (TD-bundled-executor-inproc-capability-advertisement), and carries the node-config schema as an embedded JSON Schema string (TD-node-config-schema-format-go).

Operator config: allowlists (MCP server references; env-var names for expose-env) and other runtime knobs are read from the claude-agent process's env at handler construction, under the `RIMSKY_CLAUDE_AGENT_*` prefix per TD-operator-env-namespaced-per-service. Same env-var names in both modes per TD-env-var-convention-across-modes; unset values yield open defaults per TD-allowlist-defaults-open.

Per-dispatch node config: `cli.mcp_servers` (inline entries covering http / stdio / module transports per TD-claude-agent-cli-mcp-servers-inline-only), `cli.expose_env` (per TD-claude-agent-cli-expose-env-field), `cli.required_signoffs` (unchanged), prompts, and other existing knobs. At dispatch the handler intersects each node's declared MCP list with the operator MCP allowlist and each node's declared expose-env list with the operator expose-env allowlist. A mismatch returns an executor error naming the disallowed entry. For each allowed env-var name, the handler reads its current value from the claude-agent process's env and adds it to the spawned child's env alongside callback plumbing.

### Per-node schema

The schema currently at `code:lib/services/executors/claude-agent/src/expected-attributes-schema.ts` (post-port: an embedded JSON Schema in the Go handler package per TD-node-config-schema-format-go) is updated:

- `cli.mcp_servers`: `{ref}` alternative deleted. The remaining `anyOf` covers three transports via a required `transport` discriminator: `{transport: "http", name, url, headers, allowed_tools}`, `{transport: "stdio", name, command, args, env, allowed_tools}`, `{transport: "module", name, module, allowed_tools}` — where `transport: "http-loopback"` is accepted as an alias for `module` matching the current source union (TD-claude-agent-cli-mcp-servers-inline-only).
- `cli.expose_env`: new field, `["VAR_NAME", ...]` (TD-claude-agent-cli-expose-env-field).
- `cli.required_signoffs`: unchanged.
- Everything else unchanged.

### Env-var convention across modes

TD-env-var-convention-across-modes: bundled service handlers read the same operator env vars in both modes. Containerized deployments set the env vars on the service container. All-in-one deployments set them on the all-in-one process's env (or leave them unset for zero-config defaults per TD-allowlist-defaults-open). Rimsky.yml is not changed to carry per-service config paths or content. If a user needs to mix bundled in-proc services with external services under all-in-one, rimsky.yml's existing `executors:` and `claim_producers:` blocks continue to name the external endpoints — unchanged from today.

Env vars introduced by this spec are namespaced under `RIMSKY_<SERVICE>_*` per TD-operator-env-namespaced-per-service. Surviving generic per-executor envs (`RIMSKY_EXECUTOR_PORT_*`, etc.) are relevant only to standalone gRPC deployment and don't fire in-proc, so no cross-service collision arises.

### Retirement

- The TypeScript claude-agent implementation and its build machinery (TD-typescript-claude-agent-retirement). The HTTP-JSON bridge surface is preserved by the Go port (TD-http-bridge-preserved); the bridge's port env (`env:RIMSKY_EXECUTOR_PORT_HTTP`) and HTTP shape are unchanged.
- `env:RIMSKY_EXECUTOR_MCP_CATALOG`, `env:RIMSKY_EXECUTOR_MCP_ALLOW_INLINE` — retired via TD-claude-agent-cli-mcp-servers-inline-only; replaced by `env:RIMSKY_CLAUDE_AGENT_MCP_ALLOWLIST` per TD-operator-env-namespaced-per-service.
- `env:RIMSKY_CLAUDE_AGENT_EXPOSE_ENV` — renamed and reshaped to `env:RIMSKY_CLAUDE_AGENT_EXPOSE_ENV_ALLOWLIST` per TD-operator-env-namespaced-per-service.
- The `{ref}` shape in `cli.mcp_servers`.
- Scenario tests referencing retired env vars or the `ref` shape — rewritten. Discovery grep patterns for the plan phase: `RIMSKY_EXECUTOR_MCP_CATALOG`, `RIMSKY_EXECUTOR_MCP_ALLOW_INLINE`, `RIMSKY_CLAUDE_AGENT_EXPOSE_ENV` (all callers of retired env vars) and `mcp_servers.*ref:` / `"ref"` inside `cli.mcp_servers` fixtures (all callers of the retired `ref` shape), searched across `lib/services/executors/claude-agent/`, `lib/services/test/`, `lib/services/test/scenarios/`, and `examples/`.
