# Intent Dossier: service

Distilled 2026-07-13 from session transcripts (2026-06-12..2026-07-13) and ok-planner
history artifacts (2026-05-04..2026-06-11). Transcript tier outranks artifact tier;
later intent supersedes earlier. Part of the drift-remediation intent ledger.

## Net position

- A service is an out-of-process gRPC binary implementing one or more rimsky service protocols, orchestrated by rimsky; "service" replaced "peer" as the umbrella noun (2026-05-12, nomenclature-resolution, artifact). A service is registered once with a protocol list and may implement any combination of protocols; the template slot says how a template uses it, the protocol list says what it can do — code must never conflate these axes or assume a service in one slot lacks another protocol (2026-06-19, 08d65bfe, transcript, user).
- Bundled services live in-tree as the fourth Go module `lib/services/`, requiring only `lib/protocols` among in-repo modules — the module graph itself enforces consumption-side isolation, with the depguard rule retained as defense-in-depth (2026-05-27, services-reintegration, artifact). Their integration tests live at `lib/services/test/`, and the harness consumes locally-built image tags so it always proves current source (2026-05-27, artifact).
- Bundled executors are Go (the TypeScript claude-agent is retired), with gRPC implemented as a shim on the standard in-process interface, so the same handler code runs fully bundled in-process for all-in-one and standalone for multi-container (2026-07-01, 8a8539a4, transcript, user: "port to go. easier to maintain anyway."). In all-in-one they register utility-shaped — always registered, no kind-to-URL binding required — via a lib/services `bundled.RegisterAll` entrypoint over protocols-only interfaces, with the services import confined to the cmd group (2026-07-01/03, 8a8539a4 / 3f71f90a, transcripts).
- Configuration splits into what a node needs versus what the operator permits: per-node declarations live in node config owned by the template author; operator policy gates live at deployment level; rimsky.yml stays universal — name-to-URL plus connection-level fields only (endpoint, TLS, transport, protocols, observability), treating service names as opaque and never aware of any specific service implementation (2026-07-01/03, 8a8539a4, transcript, user).
- Operator policy allowlists are rimsky-inert: enforced by the services themselves, never by rimsky; a policy rejection surfaces as a normal executor error; no policy field may appear in rimsky's protocol surface, and service internals behind the protocols must not be exposed to rimsky (2026-07-01, 8a8539a4, transcript, user). Absent policy defaults open — defaulting closed is a falsifier (2026-07-01, transcript, user).
- Rimsky is never handed secrets to substitute on behalf of executors; services get secrets from their own environment (2026-07-01, 8a8539a4, transcript, user). Store connection config (e.g. postgres connection strings) is never handled by rimsky in either mode — it lives in the store's own config, resolving env refs at store-load time (2026-07-01, transcript, user).
- In self-host/all-in-one mode the CLI talks to itself through its own control-api over loopback HTTP (single client code path proving the one public contract); only the operator surface goes through HTTP — bundled service dispatch stays in-process through the registries (2026-07-04, 3f71f90a, transcript).
- An operator-deployed standing service participates in the internal service↔service trust boundary: under `peer_auth: none` (default) its dials are plaintext on a trusted subnet; under `peer_auth: mtls` it enrolls with a `service:enroll` api-key for a short-lived cert and both peers of every dial mutually authenticate. This is orthogonal to the per-peer `tls` config key (server-cert verification against system roots). The outbound-egress SSRF guard stays a bundled-image property, not rimsky core (2026-07-16, peer-auth-posture, transcript; see the peer-auth dossier).
- The protocols module carries only stdlib, grpc, and protobuf dependencies so external authors implement without rimsky's transitive deps (2026-05-04, service-protocol-contract, artifact). lib/services Go code is AGPL; lib/protocols is the Apache island (2026-05-27, artifact).

## Required behaviors (open promises)

- Each declared service protocol is probed at startup via the Capabilities handshake, with operator-declared properties validated against the service-declared envelope (2026-05-04, service-protocol-contract, artifact; the "cached for process lifetime, restart to change" clause is superseded — see below).
- Bundled in-proc registration semantics: unconfigured services skip with a log line; present-but-invalid config aborts boot naming the handler; config-declared names always win over bundled in-proc handlers; bundled discovery entries are static so the refresh loop cannot wipe them (2026-07-03, 3f71f90a, transcript). Hybrid deployments (bundled in-proc plus external by endpoint) are supported with rimsky.yml unchanged (2026-07-03, 8a8539a4, transcript, user).
- Bundled handlers read the same service-owned env vars in both modes (env-var convention across modes) (2026-07-03, 8a8539a4, transcript, user). Claude-agent operator allowlists are namespaced env vars (`RIMSKY_CLAUDE_AGENT_EXPOSE_ENV_ALLOWLIST` and the MCP analog) parsed at handler construction, intersected against per-node declarations at dispatch; unset means open (2026-07-03, 8a8539a4, transcript).
- Per-node MCP servers are declared inline in node config (transports http, stdio, module; http-loopback aliases module) plus per-node expose_env; the service enforces the intersection with the operator allowlist and rejects off-allowlist dispatches with an error naming the disallowed entry, template, and node — no operator-side keying by node name, no MCP field in rimsky's dispatch payload (2026-07-01/03, 8a8539a4 / 3f71f90a, transcripts). Per-node service configuration rides the existing dispatch payload — no new protocol or payload fields; this is a bundled-services story, not a rimsky story (2026-07-01, transcript, user).
- Cross-mode proofs: the same template file bytes driven in self-host in-process and containerized all-in-one reach the same terminal-graph shape; per-node MCP/expose-env divergence proven at scenario level; the single-process proof asserts no external service process was contacted (2026-07-04, 3f71f90a, transcript).
- The claude-agent executor is fully async under the unary protocol: Execute returns AwaitAsyncCallback with an async_ack_id; the verdict POSTs to /v1/callback/{ack}; keepalives to /v1/runs/{id}/keepalive; session token rides attributes_delta.session_token only (2026-06-17, b31002b8, transcript). The env-passthrough security invariant — rimsky never sees the plaintext — survives the mechanism change (2026-07-03, 8a8539a4, transcript).
- Spawned local service binaries must honor the `RIMSKY_AGENT_PORT` contract: every bundled production binary checks RIMSKY_AGENT_PORT first, falling back to its own port var (2026-06-21, ecde6dd1, transcript — see drift record). compose run and self-hosted `rimsky run` spawn late-bound `--service` binaries directly via hostagent.SpawnService (no separate daemon, no proxy) and must not leak processes — spawned services are gone after the run exits, proven by scenario test (2026-06-13/14 + 2026-07-03, 65667e33 / f0176bde / 8a8539a4, transcripts).
- The compose manifest carries its own `services:` block for static executor endpoints (single-file one-shot runs) and validates service-name shape `^[a-z][a-z0-9-]{0,62}$` at flag-parse time (2026-06-13/14, 65667e33 / f0176bde, transcripts).
- Multi-role binaries register under each role's namespace in rimsky.yml, reusing the same name pointing at the same endpoint; role separation is achieved by deploying two named instances, not new config surface (2026-05-19, multi-instance-template-ergonomics, artifact-only).
- The `tls` config key exists on executor, store, and publisher entries and is honored at every peer dial site; `required` verifies against system roots with failures naming the peer and mode; HTTP-transport executors under required must declare https:// (2026-06-11, last-mile-stability, artifact — "a security-shaped config key that is accepted and ignored manufactures false confidence").
- Validation mix-in: a service implements a single Validate RPC advertised in its capabilities; rimsky calls it at template registration with role context; error findings block registration, warnings surface without blocking (2026-06-08, corpus-bootstrap, artifact-only).
- The host-agent-proxy is a normal multi-protocol service from rimsky's perspective; no tunnel-awareness leaks into the supervisor, dispatch path, error vocabulary, or graph processing (2026-05-24, host-agent-and-proxy, artifact).
- Utility executors (loop, timer, logic gates) run inline with the scheduler/runtime process as internal embedded executors implementing the executor protocol — not distributed images (2026-06-14, 752fe200, transcript, user).
- Bundled claim producers support partition_request fan-out shapes: filesystem — `list`, `batch_pick`, `expand_folder`, unknown shapes rejected InvalidArgument; postgres — `list` and operator-pre-declared `partition_policy` references, zero SQL in the authoring surface (2026-06-18, 9fb55f08, transcript).
- verifier-shape-checks ships as a bundled Go executor (no_nulls, pk_unique, value_in_set, regex_match, numeric_range, …) advertising both executor and validator roles (2026-06-15, 8c66c02c, transcript; license per the 2026-05-27 AGPL decision, not the archived spec's Apache label). The four recovered executor stories (signoff-binds-real-output, mcp-catalog-transports, claude-agent-error-classes, validator-header-secret-refs) belong in the core catalog — bundled executors are part of the project (2026-06-15, 8c66c02c, transcript, user).
- The four bundled sensors (cron, http, object-store, webhook) ship as deployable artifacts (2026-05-17, sensor-messaging-unification, artifact-only; sensor as a service kind — 2026-05-15, data-platform-extensions, artifact-only).
- The claude-agent image is Wolfi-based (cgr.dev/chainguard/wolfi-base, USER nonroot 65532, tini) (2026-05-29, cve-remediation, artifact-only), and the Docker Scout critical/high scan gate is never relaxed to mask findings — unfixable findings get documented and decided by a human (2026-05-29, artifact).
- The single-process-all-in-one and claude-agent story Proofs were explicitly rewritten to exhibit bundled in-proc dispatch with no external service processes, and the Go handler with per-node MCP, expose-env, sign-off gating, and no plaintext env in the persisted bag (2026-07-03, 8a8539a4, transcript, user: "B").
- Bundled stores ship no-op LifecycleSubscriber implementations behind an opt-in enable_lifecycle flag (2026-05-04, layer-crystallization, artifact-only).

## Intentional absences

- **A generic `services:` block in rimsky.yml.** Operator config disambiguates by protocol (`claim_producers:`, `executors:`) even though the umbrella concept exists (2026-05-12, nomenclature-resolution, rejection). The compose manifest's `services:` block (2026-06-13) is a different surface and does not reverse this.
- **A shared CapabilitiesProvider Go interface.** Rejected; N protocols means N handler types registered separately, composition-site resolution (2026-05-12, rejection).
- **The TypeScript claude-agent executor and its npm/tsc machinery; `RIMSKY_EXECUTOR_MCP_CATALOG`, `RIMSKY_EXECUTOR_MCP_ALLOW_INLINE`, `RIMSKY_CLAUDE_AGENT_EXPOSE_ENV`; the `{ref}` catalog shape in cli.mcp_servers.** All retired atomically with the Go port, pre-v1, no shims; only inline MCP entries remain (2026-07-03, 8a8539a4, transcript, reversal).
- **Rimsky-side enforcement or knowledge of service policies.** Rimsky must not know about policies it cannot enforce (2026-07-01, 8a8539a4, transcript, user). This also voids the interim direction to rewrite rimsky.yml as an allowlist and the proposal to add an opaque `config:` path field to per-protocol entries (superseded 2026-07-03).
- **Service-schema-specific config bytes in rimsky.yml.** Confirmed it never existed and is to be preserved as absent; no production code branches on names like claude-agent (2026-07-03, 8a8539a4, transcript, user).
- **Host-agent daemon auto-start for `--service` under self-host (option B1).** Superseded by direct hostagent.SpawnService (B2') (2026-07-03, 8a8539a4, transcript, user).
- **Host-agent-proxy in one-shot mode.** It bridges a remote stack to a dev box; in one-shot mode the supervisor is already local (2026-06-13, 65667e33, transcript).
- **Coding-agent orchestration bundled into rimsky-core.** Lives in a standalone consumer project; core contributes the platform primitive (compose run + local-binary spawning) and stays project-agnostic (2026-06-13, 65667e33, transcript).
- **A dataset-version RPC on the openlineage subscriber.** Deliberately poller-only as its V1 transport; the story clause never had code; adjudicated fix-doc, finding 1958 (2026-07-13, 3f71f90a, transcript).
- **Bundled-service imports of core internals.** Denied by the consumption-side-isolation depguard, deliberately kept as a guard against re-bundling (2026-05-24/27, artifacts).

## Corrections and restorations (drift-fight record)

- **RIMSKY_AGENT_PORT contract drift**: the documented spawn contract was honored only by test stubs — zero bundled production binaries read it (sensor-cron read RIMSKY_SENSOR_CRON_PORT, claude-agent read RIMSKY_EXECUTOR_PORT_GRPC), so `rimsky run --service` with any bundled binary silently returned spawn_failed. Ruled: the contract is real design; fix the binaries (check RIMSKY_AGENT_PORT first, fall back), then document honestly (2026-06-21, ecde6dd1, transcript).
- **"Pre-existing bit-rot" label rejected**: the OpenLineage empty-job.name and pg_error_classes instance:true failures were regressions from earlier deliberate refactors (commits 80a11733, c6907c29) that swept immediate consumers but not downstream services-integration consumers; regressions must be traced to their originating commits and recorded (2026-07-06, 3f71f90a, transcript, user). Precedent for adjudicating services-side breakage.
- **sql-checks verifier attribute loss**: compileNoNulls/compilePKUnique wrote []string into Result.Counts, which structpb.NewStruct silently rejects, so every no_nulls/pk_unique dispatch arrived with empty attributes_delta; fixed by materializing []any — verifier results must reach attributes_delta intact (2026-06-17, b31002b8, transcript).
- **Utility-executor packaging correction**: the proposal to ship loop/timer/gate executors as bundled-service images was corrected by the user to inline in-process embedding (2026-06-14, 752fe200, transcript).
