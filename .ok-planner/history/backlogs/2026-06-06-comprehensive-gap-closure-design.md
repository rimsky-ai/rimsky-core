# Rimsky Platform — Close Every Gap with Provable Finality

## Goal

Deliver all missing platform functionality and close every confirmed intent-vs-reality gap with provable finality. The three 2026-06 audits surfaced 53 candidate gaps: features that a completed spec or plan promised, that an operator can read about (in a spec, concept doc, CLI flag, API field, config key, docstring, or declared error class) and reach for — only to find it absent, silently ignored, or behaving the opposite of the design. After review, 41 of those are confirmed (12 were removed — 11 as genuine future work, flagged in a spec as later/V2/“can be added later” and never part of a deliverable, or as resting on a wrong premise; 1 as subsumed by a better fix), and two further gaps surfaced during review (completing the `examples/` module's one-per-protocol coverage; mandatory instantiation-time validation), for 43 user-outcome stories. This spec enumerates each as a user-outcome story.

## How it works

This is a single spec, turned into a single plan by `write-plan`, executed as a single run. Every user-outcome story below becomes its own end-to-end acceptance gate. Each gate runs the assembled product to a real observable effect at a real surface, with the value-delivering component real (no stub standing in for the thing under test). The run cannot close until every gate is green. The completeness contract is the load-bearing property: nothing in the audits may be omitted, and no acceptance may be stated at the implementation level ("handler registered", "returns 200", "class declared") — every acceptance is the thing a user observes.

## Scope boundary

- **IN:** every capability promised by a completed spec or plan — including capabilities a spec tucked under its own "out of scope / V2 / future" heading. Those deferrals were never sanctioned by the project owner; they are un-deferred here.
- **OUT — forward-facing sketch-only, never in a completed spec/plan:** package manager + catalog, `geo` blessed typed-attribute, the Rimsky Development Kit (Python `rimsky-rdk` / `python-runtime`), OpenTelemetry distributed tracing, SSE event streaming (`GET /events/stream`, LISTEN/NOTIFY), template-level `messages:` schema, durable audit-log spool/shipper, dynamic executor/claim-producer registration endpoints, the unified child-execution primitive + `carry_verbatim`, executor subprocess-lifecycle events, heartbeat enrichment columns, one-message-per-frame invariant, multi-tenant substore provisioning, `report_await_async_callback` MCP tool, `_rimsky.run_scope.*` reserved attributes, reactive-nomenclature rework, cheap-test stub compose profile + synthetic-blocker, bundled-store `SplitScope` (the 2026-05-28 sketch — `concept:fan-out` correctly puts split-scope on the producer, and the bundled stores rejecting a `fan-out:` node at registration is the shipped concept's documented behavior, not a broken completion). These are dropped.
- **OUT — already fixed in current code:** the `rimsky_messages.sender_kind` CHECK (now `('operator','publisher','instance')`), and the callback-determinism TOCTOU window (closed when `applyTerminal` was rewritten to accept the outer tx). These are dropped.

**Acceptance:** With a real sensor-cron binary configured with `RIMSKY_SENSOR_CRON_STATE_DSN` pointing at a real Postgres (testcontainers): register a cron publisher-subscription whose `next_fire_at` is in the future, then kill and restart the binary BEFORE rimsky's `ResyncPublisherSubscriptions` would re-issue Subscribe. The value-delivering component (the real sensor-cron Publisher service backed by a real Postgres state DB) is exercised end to end.

#### S-sensors-cron-replica-posture-accuracy — As an operator, I can trust that the documented sensor-cron replica posture matches the binary's actual firing behavior: a single replica fires each cron window exactly once, and the platform makes no claim of cross-replica advisory-lock coordination that the code does not deliver, so that I read one honest contract instead of being misled by a stale advisory-lock promise into running two replicas and silently getting double invalidations.
**Acceptance:** An automated accuracy check runs the real sensor-cron binary's Publisher service end to end against a real message-receiver: (1) one running SensorService instance with a due cron publisher-subscription, when ticked, POSTs exactly one publisher message envelope per fire window (`sender_kind="publisher"`); (2) two independently-running SensorService instances sharing one `publisher_subscription_id`, each ticked over the same window, together POST exactly two envelopes — proving the honest N-times fan-out the `concept:replica` contract documents; (3) the check asserts no advisory-lock / DB-coordination primitive exists in the sensor-cron source (no `pg_advisory*`, `GET_LOCK`, leader election), so the documented single-replica posture is provably the implemented behavior. The value-delivering component (the real sensor-cron Publisher service firing real message POSTs) is exercised, never stubbed.

## Design changes

The following stories carry design-doc updates or tension resolutions. Each is applied alongside the conforming code by `execute-plan`; all references are path-free per the concept self-containment rule.

### Tension resolutions

- **`tension:compose-prefix-client-side`** (S-control-api-mcp-compose-prefix-server-guard) — resolution: move the `compose:` prefix reservation from a client-side CLI convention to a server-enforced boundary on tag-create and instance-create. Record in `concept:tag` (and `concept:control-api`) that the reservation is a server-enforced invariant, not a CLI courtesy.
- **`tension:anonymous-mode-locks-out-late-bind`** (S-hostagent-anonymous-mode-latebind) — resolution: define how a late-bound dispatch resolves the serving agent when the instance has no api-key owner (e.g. routing by an anonymous-mode agent registration / a default agent), removing the hard mutual-exclusion. Update `concept:host-agent-proxy` and `concept:anonymous-mode`.

### Concept-doc updates

- **`concept:write-semantics`** (S-executors-signoff-binds-real-output) — clarify that the sign-off gate binds the run's effective bound attributes (terminal-final delta merged with any incremental `attributes_set` writebacks), not whatever rides `report_complete`; the executor must reconstruct the bound value the supervisor will commit, which on the incremental path means the accumulated writeback state.
- **`concept:dry-run`** (S-auth-identity-bound-dryrun) — reverse the 2026-05-29 decision ("the flag is the only source of dry-run; the grant carries no mode"). Make dry-run resolvable from EITHER the request flag OR an identity-bound grant mode, with the grant mode a floor the caller cannot escalate past.
- **`concept:permission`** (S-auth-identity-bound-dryrun, S-auth-grant-scope-enforced) — restore a `mode` field on grant entries and an evaluator that surfaces the matched entry's mode (un-deferring the per-grant mode modifier); and add a `scope` field to the grant entry shape with scope-match semantics (resource selector evaluated alongside the action match) plus an invariant that a scoped entry allows only requests whose target resource satisfies the selector. The 2026-05-15 spec's V2 deferral of resource scoping is un-deferred per the scope boundary.
- **`concept:cascade` / `concept:invalidate`** (S-cascade-operator-frame-in) — define the operator-originated in-frame invalidate: an operator `frame: in` request must resolve the target instance's currently-running frame and join it (mark target stale with that frame_id), with a deterministic, documented fallback to next-frame only when no frame is currently running. Name the boundary between operator-sourced and cascade-sourced in-frame joins.
- **`concept:lifecycle-subscriber`** (concept clarification — no code story; doc-accuracy) — state the protocol's scope explicitly in Definition/Boundaries: it relays the **control-plane / instance lifecycle** (template register/deploy/undeploy/deregister, instance created/terminated, run-scope terminal) and deliberately does **not** carry node-cascade events (individual node-run transitions such as parked), which live in `concept:signal` / `concept:event-log` — so the omission is an intentional boundary, not an arbitrary subset. Also correct the over-claim that the bundled postgres store applies per-template DDL on the deployed callback: it ships a no-op skeleton (a documented fork-point), so DDL-on-deploy is the archetype the protocol enables, not a shipped behavior.
- **`concept:signal`** (S-cascade-waitset-topic-taxonomy) — align the wait-set `topic_kind` discriminator with the canonical 5-value signal taxonomy (the deferred CHECK-broadening migration from the 2026-05-23 signal-taxonomy reshape), removing the lossy 3-bucket collapse so `topic_kind` is a faithful projection of the signal top-level kind.
- **`concept:host-agent-proxy`** (S-hostagent-per-run-scope-isolation) — make the run-scope-keyed-spawn invariant real: one spawn per (run-scope, binding), run-scope lifetime, reaped on run-scope termination. Requires threading `run_scope_id` onto the dispatch wire so the proxy can key on the real run-scope rather than the instance id.
- **`concept:host-agent-proxy`** (S-hostagent-latebind-all-protocols) — state protocol-transparency as a proxy invariant: the proxy is a transparent forwarder of every rimsky service protocol it fronts (executor, claim-producer, publisher, validation, data-processing), each presenting exactly the fronted service's protocol, forwarded by one uniform mechanism — no protocol ships as a registered-but-unimplemented stub, and no per-protocol special-casing leaves some protocols unable to reach the spawn/forward path. A service that conforms to its own protocol therefore works behind the proxy by construction — the proxy adds no separate conformance surface, so there is no host-agent / proxy conformance suite.
- **`concept:template` / `concept:instance`** (S-template-validation-ref-validation-mode, S-template-validation-instantiation-mandatory) — record the validation-timing model: reference/schema validation is **optional at registration** (operator-mode-controlled, since referenced services may not yet exist) and **mandatory at instantiation** (committing to run the template means all referenced services exist — the bound-on-demand host-agent proxy is itself a present service), where the statically-knowable config is fully validated (value constraints included) and a misconfigured instance is rejected before it runs. Dispatch already validates the resolved bag (`@blessed-invariant 12`, validate-twice) and continues to — it stays necessary for substitution-sourced values knowable only at dispatch — so this adds an earlier instantiation gate for the static config, with the dispatch pass becoming defense-in-depth for that static part.

(Stories whose `designChange` is "none" — including S-claimproducer-9b-probe, S-claimproducer-scopesconflict-wired, S-fsstore-atomic-staging-reference, S-pgstore-atomic-staging-substrate, S-pgstore-claim-unavailable-swap-failed-emit, S-sensors-cron-replica-posture-accuracy, and S-sensors-cron-state-dsn-durability — already match an existing concept boundary/invariant and require only code conformance, not a concept-doc edit.)
