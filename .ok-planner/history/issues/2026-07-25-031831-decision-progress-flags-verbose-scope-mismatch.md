# TOC credits --verbose with scheduler decisions and claim-handle events the body does not state

## Problem

decisions.md says '--verbose adds frame ticks, scheduler decisions, and claim-handle events'; the body says frame-tick lines only on top of the default lines.

## Candidates

- Regenerate the TOC from the body
- Restore the body if --verbose actually surfaces more

## Discussion

`decision:progress-flags`'s own body squarely answers this, and the code confirms it: "`--verbose` adds frame-tick lines on top of the default instance-starting / node-run-terminal / instance-terminal lines." No mention of scheduler decisions or claim-handle events.

Code: `code:cmd/rimsky/cli/compose/progress.go` defines the `ProgressPrinter` interface with exactly six methods (`InstanceStarting`, `NodeRunTerminal`, `InstanceTerminal`, `FrameTick`, `Summary`, `Finalize`) — there is no scheduler-decision or claim-handle-event method anywhere on the interface or its implementations. The `verbosePrinter` type (`progress.go:116-124`) overrides exactly one method relative to the embedded default `linePrinter`: `FrameTick`, which emits `"instance %s/%s frame %d"`. `quietPrinter` and `jsonPrinter` are the only other variants; nothing in the file prints a scheduler decision or a claim-handle event under any flag combination.

So `decisions.md`'s TOC one-liner — "`--verbose` adds frame ticks, scheduler decisions, and claim-handle events" — is the stale artifact here: it over-states scope relative to both the decision's own body and the shipped CLI behavior. `decisions.md` is explicitly a generated index ("Generated by execute-plan when a plan touches `decisions/`. Do not edit by hand — changes will be overwritten"), not itself authoritative content, so this is a mechanical regeneration case rather than a design question: a future sprint should regenerate the TOC line to match the body ("adds frame-tick lines on top of the default lines"), not the other way around — the body is confirmed correct by the shipped `--verbose` behavior.

Closing this issue as answered by `decision:progress-flags`'s own body, cross-confirmed by `code:cmd/rimsky/cli/compose/progress.go`.
