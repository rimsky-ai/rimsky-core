# Fan-out: partition split, sub-claim atomicity, aggregation policy, and clone cancellation

Unsupported, on the cancellation invariant. Thirteen of the fourteen invariants hold and were each checked against the acquire, dispatch, and settlement paths. Registration rejects a fan-out whose named claim is not declared on the node and rejects one whose producer does not advertise split-scope support, both with unit tests, including the case where the claim arrives through a co-holdership alias. The partition request is resolved through the ordinary substitution context at acquisition and passed to the producer opaquely. Sub-claim acquisition happens inside the parent-acquisition transaction, upstream of dispatch, and the dispatch primitive receives already-acquired sub-claims and never calls split. The data-processing candidate-begin fires inside that same transaction with an unwind path that abandons begun candidates on failure. A split returning zero descriptors falls through the fan-out branch entirely and the node dispatches as an ordinary leaf holding the parent claim. A clone does not re-fan-out: the guard reads the run scope and returns early only when the scope carries both a parent run and a non-empty partition key, so a sub-graph scope still fans out. Disjointness is enforced producer-side — the shared list-partition grammar rejects duplicate keys and unknown top-level keys. Per-partition attribute writebacks are not merged onto the parent, and the producer-metadata channel the invariant points to instead exists on the child-settlement path. A fan-out node may also declare a delegate, and that combination validates cleanly. The parallelism cap is an in-process semaphore registry keyed by parent run, acquired immediately before the synchronous executor call and released when it returns, so it is per-process and not pooled, as claimed. What is not carried is the claim that `strict` and `first` both force-cancel every remaining in-flight clone at the run level. Only `first` does: its aggregate result carries a cancel-non-winners action that the cancel executor consumes, recursing into each loser's run subtree and transitioning it to failed. `strict` produces a distinct cancel-siblings action that the same executor explicitly skips — nothing anywhere consumes that action value — so under `strict` the only cancellation that happens is a claim-handle-level force-abandon of the siblings' sub-claims, which leaves each sibling clone's run row untouched and still in flight. The sole scenario test for the strict path asserts the action value returned by the aggregator, not that anything is cancelled.
