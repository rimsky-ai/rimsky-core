# Changelog

## Unreleased

- **Review cleanup (24 issues)**: Fixed a protocol incompatibility where the TS claude-agent executor POSTed async callbacks to the supervisor's base URL with body key `kind`, but the Go supervisor routes `/v1/callback/{ackID}` and reads body key `type` — all async callbacks would have 404ed in production. The TS executor now appends `/v1/callback/{async_ack_id}` to `callback_url` and uses `type` in the body; a new end-to-end test in `executors/claude-agent/src/server.test.ts` exercises the real network round-trip against a fake supervisor matching the Go chi route. Added `SupervisorConfig.CallbackAdvertiseHost` / `CallbackAdvertisePort` (plus `RIMSKY_SUPERVISOR_CALLBACK_ADVERTISE_HOST` / `_PORT` env vars and `callback.advertise_host` YAML) so the supervisor can advertise a peer-reachable hostname in container deployments (listener binds `0.0.0.0` but executors can't dial that); `deploy/docker-compose.yml` and `deploy/supervisor-config.yml` are updated. Added `node.ReasonInfraReenqueue` (running→stale, no retry bump) to distinguish terminal-outcome infra re-enqueues from the scheduler's heartbeat-lost sweep; `terminal_outcome.go` uses the new reason. Threaded `SupervisorID` through `OnErrorArgs`, `CommitArgs`, `ApplyTerminalArgs`, and `scheduler.InvalidateArgs` so every `Queue.RemoveForNode(...)` call is now claimant-guarded instead of running unguarded. Operator-originated invalidates (reason prefixed "operator") that hit a running node now set `kill_requested=true` so the subprocess can be cancelled by the supervisor's heartbeat tick, documented in `docs/operator-guide.md`. Callback handler re-registers the async ack on `ApplyTerminalOutcome` failure so executors can retry instead of stranding the node in `running`. `migrations/runner.go` unlock now uses `context.Background()` so a cancelled parent ctx doesn't leave the advisory lock held. `schedule_ticker.go` advances cron from `row.NextFireAt` (not `clock.Now()`) — missed fires are no longer backfilled; the three `schedule_dispatch_failed` event appends now include `InstanceID`. Removed the dead `ClearSupervisorAssignment` call in `sweepStaleHeartbeats` (UpdateState already clears it). Replaced the 50ms-polling Shutdown wait with a `sync.WaitGroup` and removed the redundant nested `defer cancel()` in the dispatch goroutine. Renamed `chiItoa` → `portToStr`. Fixed protocol.md inaccuracies: execute endpoint is `/v1/Execute` (not `/v1/nodeexecutor/execute`); the async-callback section now documents the real URL/body shape (path-embedded ackID, flat body keyed by `type`, 200 OK response). Docs/tests purged of zonebase vocab (`parcels` → `items`, `zone` column → `category`, Phoenix → project-alpha, zonebase_production → analytics_production); README consumer-agnostic for OSS extraction; `executor-author-guide.md` Python example reorganized so `BadInputError` is defined before its `except` clause and the `yield ...; return` lines are split. `state_test.go` extended with `ReasonInfraReenqueue` row. All tests pass (Go + TS).
- Polish T6 (P4): exercised `docker compose up` live against fresh images and removed the obsolete top-level `version: "3.9"` key from `deploy/docker-compose.yml` (Compose v2 ignores it and emits a deprecation warning). Fixed three env-var mismatches surfaced by the smoke test so the stack comes up within 60s and a `greet` node reaches `fresh` in 1s: (1) `migrate` / `scheduler` / `supervisor` / `control-api` now receive `RIMSKY_DB_URL` instead of `RIMSKY_POSTGRES_DSN` (the binaries all read `RIMSKY_DB_URL`), (2) `scheduler` now uses `RIMSKY_SCHEDULER_TICK_MS` instead of `RIMSKY_TICK_INTERVAL_MS`, (3) `control-api` now sets `RIMSKY_CONTROL_API_HOST=0.0.0.0` + `RIMSKY_CONTROL_API_PORT=8080` instead of `RIMSKY_HTTP_ADDR`, (4) `supervisor` now sets `RIMSKY_SUPERVISOR_CONFIG` instead of `RIMSKY_CONFIG_PATH`, (5) `http-node` env rewritten to `RIMSKY_EXECUTOR_HTTP_NODE_HOST/PORT/HTTP_PORT` + `RIMSKY_EXECUTOR_STUB_MODE=1` (was stray `RIMSKY_GRPC_ADDR` / `METRICS_ADDR`), (6) `claude-agent` env rewritten to `RIMSKY_EXECUTOR_HOST` / `RIMSKY_EXECUTOR_PORT_GRPC` / `RIMSKY_EXECUTOR_PORT_HTTP` + `RIMSKY_EXECUTOR_STUB_MODE=1` (was stray `GRPC_ADDR` / `METRICS_ADDR` / `CLAUDE_STUB_MODE`). Rewrote `deploy/supervisor-config.yml` to the shape actually consumed by `core/cmd/rimsky-supervisor/main.go`'s `yamlConfig` struct: top-level `postgres_url: "${RIMSKY_DB_URL}"`, `concurrency`, `heartbeat_interval_ms`, `callback: {host, port}`, and `executors:` as a map keyed by executor name (was a list under `supervisor:` / `executors:` sections that didn't match the struct tags). The Kubernetes Helm chart templates under `deploy/kubernetes/rimsky-chart/templates/` have the same `RIMSKY_POSTGRES_DSN` mismatch and are NOT fixed by this change — they are out of the T6 scope and will need a follow-up.
- Polish T3 (Deviation #8): introduced the explicit `*resource.FactoryRegistry` type in `core/resource/register.go` with `NewRegistry`, `Register`, `Get`, `ListNames`, and a process-default registry accessor `DefaultRegistry`. The prior global `RegisterFactory` / `GetFactory` / `ListFactoryNames` free functions are preserved as deprecated shims over the package-default registry for backward-compat. Added `ResourceFactories *resource.FactoryRegistry` to `config.SupervisorConfig`, `config.ControlAPIConfig`, `supervisor.Config`, and `controlapi.AppDeps`; nil falls back to `resource.DefaultRegistry()`. `controlapi/templates.go` and `controlapi/instances.go` now look up factories through `deps.ResourceFactories`. Scenario harness (`core/scenario/harness.go`) constructs a per-test registry and passes it via both `SupervisorConfig` and `ControlAPIConfig`, dropping the prior `getResourceForOwner` workaround. Both reference binaries (`rimsky-supervisor`, `rimsky-control-api`) construct per-process registries and pass them explicitly. Named `FactoryRegistry` (not `Registry`) to avoid collision with the existing narrow `resource.Registry` storage-facing interface in `core/resource/interface.go`. Full suite passes; `go test ./test/scenarios/... -count=5 -race` clean. Known v1 limitation (no code change): the `GetResource` callback in both reference binaries and the scenario harness hardcodes the lookup key to `"inline-jsonb"`; a node owning multiple resources with different implementations would need a per-resource implementation switch, which is a post-v1 concern.
- Polish T1: removed the narrow consumer-side interfaces (`ScheduleBackendView`, `ScheduleStoreView`, `EventStoreView`, `ScheduleRowView`, `EventAppendInputView`) from `core/scheduler/schedule_ticker.go` and the bridging adapters (`scheduleBackendAdapter`, `scheduleStoreAdapter`, `eventStoreAdapter`) from `core/scheduler/scheduler.go`. `ProcessSchedules` now takes `storage.StorageBackend` directly and uses `storage.ScheduleRow` / `storage.EventAppendInput` — the `scheduler → storage → node → scheduler` cycle is already broken (backoff lives under `core/node/`), so the indirection had no remaining purpose. Rewrote `core/scheduler/schedule_ticker_test.go` to use the real `pgstorage` backend via `pgtest.StartPostgres` instead of in-memory fakes; the six tests (NextFireAt valid/invalid, ProcessSchedules nothing-due/fires-one/dispatcher-error/invalid-cron-skips) keep the same coverage with real storage plumbing.
- Plan C Phase 1 (Tasks 1.1–1.3): added the `external-sql` resource reference implementation at `core/resource/externalsql/`. Implements `resource.Factory` + `resource.Resource` with a staging-table + atomic-swap commit pipeline. `Factory.Create` probes the target table exists, validates quoted identifiers, and binds a named `*pgxpool.Pool` from the supervisor's `SQLConnections` map. `Commit` runs quality rules (using the current table's rows as `PreviousData` so `row_count_ratio` works cross-commit), stages via `TRUNCATE` + `jsonb_populate_recordset`, then swaps `current` ↔ `staging` ↔ `previous` inside a single transaction. `RestoreVersion("previous")` swaps current ↔ previous; `RestoreVersion("id")` returns `ErrRollbackUnsupported` (by-id staging retention is out of scope for v1). 8 tests cover happy-path, quality-rule rejection leaves current unchanged, previous rollback reverts content, by-id rollback is unsupported, concurrent commits serialize via ACCESS EXCLUSIVE, no-op commits do not truncate staging, config-error probes, and a full-lifecycle scenario (provision → commit → commit → rollback → re-commit) inline at `scenario_test.go`. Registry bookkeeping delegates to `storage.ResourceRegistry`; no supervisor-harness wiring yet (Plan C Phase 2).
- Plan C Phase 5: added the protocol conformance suite at `conformance/` plus the `rimsky-conformance` CLI at `core/cmd/rimsky-conformance/`. Seven scenarios are registered via `init()` in `conformance/scenarios/` (execute_happy_path, heartbeats, malformed_userdata, terminal_is_last, cancel, async_handoff, result_serialization, stream_close_without_terminal). Capability probing via stub-mode and async-handoff probes drives `RequiresStub` / `RequiresAsync` skip logic. `unknown_ack_id` is intentionally not registered in v1 (requires a supervisor round-trip; documented placeholder file). CLI flags: `--endpoint`, `--transport grpc|http`, `--require-stub-mode`, `--scenarios`, `--skip`, `--timeout`. Returns non-zero exit on any FAIL.
- Plan B Phase 1 (Tasks 1.1–1.6): added the `http-node` reference executor at `executors/http-node/`. Implements `NodeExecutorServer` over gRPC (default `:9091`) plus a protojson+ndjson HTTP bridge on a sibling port, with a transport-independent `executeCore` that drives both via a narrow `sendFunc`. Userdata schema: `{url, method?, headers?, body?, expect_status?}`. Error classes: `invalid_userdata`, `http_request_failed`, `http_unexpected_status`, `http_response_parse_failed`. `RIMSKY_EXECUTOR_STUB_MODE=1` short-circuits the network path (canned `{stub:true}` or `userdata.stub_response`). Zero imports from `core/*` — only `proto/v1/gen` — enforcing the three-collections separation rule. 11 unit tests cover happy-path 2xx JSON, 404/unexpected-status, network error, missing-URL, stub mode (default and custom), custom `expect_status`, non-JSON base64 fallback, invalid-JSON-with-JSON-CT, POST with struct body, and an end-to-end HTTP-bridge round-trip.
- Plan A Task 13.2: 17 end-to-end scenario tests under `test/scenarios/` covering the full orchestration surface — happy-path executor, pure-cascade, scheduled node fire, fan-out, cascade invalidate, retry-then-give_up, double-buffering with quality-rule rejection, restore-version rollback, async-handoff via callback endpoint, executor Blocked, unresolved-executor, heartbeat loss re-enqueue, orphaned-claim release, verify-before-run race, state-machine same-state rejection (blessed-invariant §17), concurrency-tag limit enforcement, and no_op commit dependent-no-cascade. Each scenario boots a dedicated Postgres container via the scenario harness.
- Moved the scenario harness from `core/internal/scenario` → `core/scenario` so `test/scenarios/*_test.go` at the repo root can import it.
- Harness: `getResourceForOwner` no longer reads from the process-global `resource.GetFactory` registry — it constructs an `inlinejsonb.Factory` bound directly to the caller's `storage.StorageBackend`. Fixes a cross-test aliasing bug where parallel scenarios each called `RegisterFactory` with their own pool, and the last Start() clobbered earlier ones, causing Commit to write to the wrong Postgres container.
- Initial Go port scaffold.
- Added `core/scheduler/schedule_ticker.go` (port of TS `timer-ticker.ts` renamed to schedule-semantics). Cron-driven invalidate dispatch for nodes with a `schedule_cron`; emits invalidate to the node itself rather than a separate target (Go port treats schedule as a node property, not a distinct cell kind).
- Plan-A event kind: `schedule_dispatch_failed` is logged when a schedule row cannot be advanced or dispatched (invalid cron, RecordFired failure, or dispatcher error). This event kind supplements the spec §11.2 list and should be folded into the spec in a post-plan amendment.
- Scheduler ticker consumes narrow consumer-side interfaces (`ScheduleBackendView`, `ScheduleStoreView`, `EventStoreView`) instead of importing `core/storage` directly. This avoids a `scheduler → storage → node → scheduler` import cycle (node policy imports `scheduler.ComputeDelay`). A thin adapter in the cmd composition layer will wrap the full `storage.StorageBackend` to satisfy these views.
- Added `core/supervisor/runner.go` (Plan A Task 10.3): single-node runner that verifies claim ownership, resolves the executor endpoint, transitions stale→running, streams `ExecuteEvent`s from the executor, and maps terminal events onto `ApplyTerminalOutcome`. Covers Complete / Errored / Blocked / AsyncAccepted plus dial-failure and stream-close-without-terminal infra-error paths. `AsyncAccepted` hands off to the supervisor's callback registry via a caller-supplied `registerAsync` function; `AsyncContext` is defined here and referenced from `callback.go`. Unresolved-executor path transitions stale→running before routing to `OnError("unresolved_executor")` so the policy chain's running→* guards accept the resulting transition.
- Added reference binaries (Plan A Tasks 14.1–14.3): `core/cmd/rimsky-scheduler/`, `core/cmd/rimsky-supervisor/`, `core/cmd/rimsky-control-api/`. Thin env-var readers (supervisor takes a YAML config file path via `RIMSKY_SUPERVISOR_CONFIG`, with `${ENV_VAR}` expansion in values) that build typed `config.*Config` structs, wire pgxpool/storage/queue/resolver, register the `inline-jsonb` resource factory (supervisor only), and call the library entry points. All three handle SIGTERM/SIGINT with a 30s graceful shutdown. Promoted `gopkg.in/yaml.v3` from indirect to direct dep.
